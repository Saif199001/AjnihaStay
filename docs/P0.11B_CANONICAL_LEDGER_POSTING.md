# P0.11-B — Canonical Ledger Posting Service

**Status:** IMPLEMENTED — controlled domain integration active  
**Phase:** P0 Financial Core  
**Scope:** Safe append-only posting primitive plus the first transaction-bound domain integrations.

## Objective

Provide one reusable service for appending `FinancialLedgerEntry` records without making the ledger a second financial-state authority.

## Contract

`post_ledger_event(...)`:

- requires existing mutation authorization;
- validates the locked P0.11 event vocabulary;
- validates non-empty event keys and two-decimal positive monetary amounts;
- normalizes ISO-style three-letter currency codes to uppercase;
- validates source/reference workspace consistency through the ledger model;
- creates an immutable ledger event;
- never mutates Invoice, Payment, PaymentAllocation, AdvanceCredit, FinancialAdjustment, LateFee, Refund, or FinalSettlement state.

## Idempotency

The database-enforced boundary remains:

```text
workspace + event_key
```

A replay with the same event effect returns the original row. Reusing the key for a different event effect raises a deterministic `ValidationError`.

A nested transaction/savepoint protects the outer transaction from a concurrent unique-key collision before the winning row is re-read.

## Transaction Semantics

The posting primitive participates in an already-open transaction owned by the canonical domain mutation:

```text
outer domain transaction
    ├─ authoritative financial mutation
    ├─ post_ledger_event(...)
    └─ commit / rollback together
```

Ledger posting does not commit independently and cannot survive an outer transaction rollback.

## P0.11-C Controlled Integrations

The first integrations are deliberately limited to two authoritative mutations:

### Invoice creation

`create_invoice()` now wraps invoice creation and ledger posting in one atomic transaction. It emits:

- event type: `invoice_created`
- event key: `invoice:{invoice_id}:created`
- amount: invoice total
- references: invoice + occupancy

### Payment recording

`record_payment()` already had an atomic financial transaction. It now posts both facts before commit:

- `payment_recorded` with key `payment:{payment_id}:recorded`
- `payment_allocated` with key `payment-allocation:{allocation_id}:created`

The allocation event is a settlement-history fact, not additional cash. The payment event records the cash-received fact; the allocation event records where that payment was applied.

If ledger posting fails, the authoritative payment/allocation mutation rolls back with it. Existing payment allocation and invoice-state semantics remain unchanged.

## Scope Deliberately Not Included

P0.11-C does **not** mass-refactor every financial service at once. Advance credit, adjustments, late fees, refunds, recurring invoice generation, and final settlement remain candidates for subsequent controlled integrations after their existing contracts are verified against their exact transaction boundaries.

No accounting/GL mappings, balances, reconciliation, or second financial-state authority are introduced.

## Regression Coverage

Tests cover:

- successful immutable posting;
- no authoritative invoice-state mutation by direct posting;
- same-key same-effect replay;
- same-key different-effect conflict;
- workspace-scoped event keys;
- cross-workspace source rejection;
- RBAC rejection for staff;
- unsupported event type;
- invalid monetary precision;
- ledger immutability;
- outer transaction rollback;
- invoice creation + ledger event integration;
- payment + allocation + ledger integration;
- payment and ledger rollback together.
