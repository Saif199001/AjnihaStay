# P0.11-B — Canonical Ledger Posting Service

**Status:** IMPLEMENTED — awaiting CI verification  
**Phase:** P0 Financial Core  
**Scope:** Safe append-only posting primitive; domain-service integration is intentionally deferred.

## Objective

Provide one reusable service for appending `FinancialLedgerEntry` records without making the ledger a second financial-state authority.

## Contract

`post_ledger_event(...)`:

- requires existing mutation authorization;
- validates the locked P0.11 event vocabulary;
- validates non-empty event keys and two-decimal positive monetary amounts;
- normalizes ISO-style three-letter currency codes to uppercase;
- validates source/reference workspace consistency through the ledger model;
- creates an immutable ledger event;
- never mutates Invoice, Payment, PaymentAllocation, AdvanceCredit, FinancialAdjustment, LateFee, Refund, or FinalSettlement state.

## Idempotency

The database-enforced boundary remains:

```text
workspace + event_key
```

A replay with the same event effect returns the original row. Reusing the key for a different event effect raises a deterministic `ValidationError`.

A nested transaction/savepoint protects the outer transaction from a concurrent unique-key collision before the winning row is re-read.

## Transaction Semantics

The posting primitive uses `transaction.atomic()` and can participate in an already-open transaction owned by the canonical domain mutation. Therefore:

```text
outer domain transaction
    ├─ authoritative financial mutation
    └─ post_ledger_event(...)
commit / rollback together
```

Ledger posting does not commit independently and cannot survive an outer transaction rollback.

## Scope Deliberately Not Included

P0.11-B does **not** mass-refactor existing financial services to post ledger events. Existing P0.1–P0.10 services and contracts remain untouched. Controlled event-by-event integration will follow after this posting primitive is proven GREEN.

It also does not introduce accounting/GL mappings, balances, reconciliation, or a second financial-state authority.

## Regression Coverage

Tests cover:

- successful immutable posting;
- no authoritative invoice-state mutation;
- same-key same-effect replay;
- same-key different-effect conflict;
- workspace-scoped event keys;
- cross-workspace source rejection;
- RBAC rejection for staff;
- unsupported event type;
- invalid monetary precision;
- ledger immutability;
- outer transaction rollback.
