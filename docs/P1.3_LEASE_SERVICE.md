# P1.3 — Lease Service

Status: **ARCHITECTURE / CONTRACT LOCKED**

## Scope

P1.3 introduces the canonical service boundary for Lease mutations. The service owns lease creation, controlled updates, and lifecycle transitions. The Lease model remains the persistence contract established in P1.2.

## Protected P1.2 Contract

- `Lease.workspace` remains a foreign key with reverse relation `leases`.
- `Lease.occupancy` remains a OneToOne relation with reverse relation `lease`.
- Workspace ownership is derived from the occupancy tenant and must match the lease workspace.
- Lease creator must be an active workspace member.
- Existing dates, financial snapshot fields, status choices, indexes, DB constraints, RLS and FORCE RLS remain unchanged.
- Renewal/version history is deferred to P1.6 and must not silently change the current OneToOne relationship.

## Canonical Mutation Boundary

All supported Lease mutations in this phase go through `leasing.lease_service`:

`request → authorization → workspace-scoped validation/locking → mutation → model validation → commit`

The service does not create or alter Financial Core state. Rent and security deposit on Lease are contractual snapshots only.

## Create

`create_lease(user, workspace, data)` validates:

- active manager-level workspace permission;
- occupancy exists in the requested workspace;
- occupancy tenant belongs to the same workspace;
- creator is an active workspace member;
- required start/end dates and non-negative rent/deposit;
- agreement/status/notice/terms fields against the Lease model contract.

The occupancy row is locked during creation to serialize competing Lease creation attempts. The OneToOne database constraint remains the final duplicate guard.

## Update

`update_lease(user, workspace, lease_id, changes)` permits only contractual mutable fields:

- agreement number;
- start/end dates;
- rent amount;
- security deposit;
- notice period;
- terms;
- agreement reference.

Workspace, occupancy, creator, lifecycle timestamps and status cannot be changed through the update service. `updated_by` is set to the acting user.

## Lifecycle

`transition_lease(user, workspace, lease_id, target_status)` is the canonical status mutation boundary.

Allowed transitions:

- `draft → pending_signature`
- `draft → cancelled`
- `pending_signature → active`
- `pending_signature → cancelled`
- `active → expired`
- `active → terminated`

A request for the current status is an idempotent no-op. Terminal states (`expired`, `terminated`, `cancelled`) cannot transition further.

Lifecycle timestamps are maintained by the service:

- active → `activated_at`
- terminated → `terminated_at`
- cancelled → `cancelled_at`

## Concurrency / Integrity

- Mutations execute inside `transaction.atomic()`.
- Lease lookup is workspace-scoped and uses `select_for_update()`.
- Creation locks the occupancy before attempting the OneToOne Lease insert.
- Cross-workspace objects are never accepted by ID alone.
- Database constraints remain authoritative for final integrity.

## Financial Boundary

Lease rent/deposit do not create invoices, payments, adjustments, late fees, refunds, ledger entries, or settlement records in P1.3. Existing P0.1–P0.12 financial contracts remain authoritative.

## Deferred

Lease API, expanded lifecycle workflows, renewal/version history, notice management, KYC, eSign, automated notifications and other P1 capabilities remain subsequent milestones.
