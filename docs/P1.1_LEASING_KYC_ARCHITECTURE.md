# AjnihaStay — P1.1 Leasing & KYC Architecture

**Status:** P1.1 ARCHITECTURE LOCKED
**Branch:** `phase-p1.1/leasing-k-y-architecture`
**Baseline:** P0.12 Financial Reporting `c3cf952f319bf11a84936d6809ec491aad75a091`
**Strategy:** India-first, globally extensible

## 1. Purpose

P1.1 defines the domain contract for Leasing and KYC without replacing the validated Property, Tenant, Occupancy, or Financial Core.

The phase extends the existing product toward:

`Property → Unit/SubUnit → Tenant → Occupancy → Lease/Agreement → KYC/Documents → Move-in/Move-out → Renewal/Notice`

The existing Occupancy remains the operational relationship with a space and period. Leasing becomes the contractual layer around that relationship.

## 2. Non-Negotiable Preservation

P1.1 must not silently change:

- Workspace and multi-tenancy boundaries
- Membership/RBAC authorization
- PostgreSQL RLS
- Property/Unit/SubUnit hierarchy
- Occupancy date and capacity semantics
- Existing Tenant semantics
- Charge, Invoice, Payment, Allocation, Advance Credit, Adjustment, Late Fee, Settlement, Ledger or Reporting contracts
- Partial payments, advance handling and arrears behavior
- Existing APIs unless a new leasing/KYC contract explicitly requires a new endpoint

Leasing and KYC consume existing domain truth; they do not become a competing financial or occupancy authority.

## 3. Leasing Domain

### 3.1 Lease ownership

A Lease belongs to a workspace and links to exactly one Occupancy. It also references the Tenant through the Occupancy rather than maintaining an independent tenant relationship that could diverge.

Conceptual model:

```text
Workspace
  └── Occupancy
       ├── Tenant
       └── Lease
            └── KYC / Documents
```

### 3.2 Lease lifecycle

Initial lifecycle states:

- `draft`
- `pending_signature`
- `active`
- `expired`
- `terminated`
- `cancelled`

State transitions must be explicit and service-controlled. A Lease becoming `active` does not itself mutate financial balances. Move-in/out remains an operational workflow that must preserve existing Occupancy semantics.

### 3.3 Lease facts

The lease contract should support, as applicable:

- agreement/reference number
- lease start date
- lease end date
- rent snapshot/reference
- security-deposit snapshot/reference
- notice period
- terms/metadata
- document/agreement reference
- lifecycle timestamps
- created/updated actor metadata

Historical contractual facts should not be silently rewritten after activation. Corrections should use an explicit amendment/version mechanism in a later contract if needed.

### 3.4 Occupancy relationship

A Lease cannot reference an Occupancy from another workspace.

A Lease must not create a second occupancy for the same tenant/space merely to represent a contract. Existing occupancy validation remains authoritative for capacity and date overlap.

Lease expiry/termination must not automatically rewrite financial history or fabricate settlement/payment events.

## 4. KYC Domain

### 4.1 KYC is a separate identity/compliance layer

Existing Tenant fields contain basic identity information and an existing `id_document`. P1.1 must not reinterpret that field as a complete KYC workflow.

KYC should become a separate workspace-scoped record associated with the Tenant, with document-level records and verification history.

Conceptual model:

```text
Tenant
  └── KYC Profile
       └── KYC Document(s)
             └── Verification History
```

### 4.2 KYC status

Initial KYC profile lifecycle:

- `not_started`
- `pending`
- `submitted`
- `under_review`
- `verified`
- `rejected`
- `expired`

Transitions are explicit and auditable. Rejection should retain history rather than erase prior submissions.

### 4.3 Document contract

A KYC document should support:

- document type
- document/reference number where legally appropriate
- secure private file reference
- issue/expiry dates where applicable
- verification status
- rejection reason
- uploaded/submitted timestamp
- verified timestamp and actor
- document metadata needed for controlled processing

Sensitive identity documents must never use public property-media delivery semantics. Access must be authenticated, workspace-scoped and authorization-controlled.

### 4.4 KYC history

Verification actions are historical facts. A later verification/rejection must not destroy the previous state history.

Document replacement should create a new document/version record rather than overwriting a historical verified document in place.

## 5. Authorization & Isolation

Workspace membership remains the canonical authorization model.

Mutation operations are restricted to the existing appropriate workspace management roles. Read access must be workspace-scoped and follow existing staff/member permissions.

All leasing/KYC records require workspace consistency checks and PostgreSQL RLS defense-in-depth.

Cross-workspace tenant, occupancy, lease or KYC references must fail deterministically.

## 6. Financial Boundary

Leasing may provide contractual inputs such as rent, deposit, dates and notice terms, but it does not become a financial transition authority.

Financial mutations continue through the canonical financial transition/service layer.

Examples:

- Creating a lease does not create a payment.
- Recording a deposit as money received remains a Payment operation.
- Applying prepaid credit remains an Advance Credit operation.
- Lease termination does not fabricate a refund.
- Final settlement remains the existing Final Settlement lifecycle.

If future leasing workflows need financial mutations, they must call the existing canonical financial services.

## 7. Move-in / Move-out Boundary

P1.1 defines the contract boundary but does not replace Occupancy.

Move-in should require a valid tenant, space and applicable lease/KYC state according to the eventual operational policy. Existing occupancy capacity/date validation remains authoritative.

Move-out should preserve the existing checkout semantics. Lease termination/expiry and occupancy checkout are related lifecycle events but must not be conflated without an explicit transition contract.

## 8. Renewals & Notices

Renewal is a contractual extension/change, not an overwrite of the historical lease.

Future renewal implementation should create a new lease/version or explicit renewal record while preserving the original agreement history.

Notice data should capture:

- notice date
- effective/end date
- reason/type
- actor
- status

Lease expiry should be derivable from contractual dates; automation/notifications belong to later phases.

## 9. API Boundary

P1.1 architecture reserves read/write API surfaces for:

- lease creation and retrieval
- lease lifecycle transitions
- KYC profile/document submission
- KYC verification/rejection
- lease expiry/renewal/notice views

Exact routes and serializers belong to implementation tasks after model/service contracts are reviewed.

No existing financial or occupancy API is replaced by this phase.

## 10. Auditability

KYC verification, rejection, document replacement and lease lifecycle transitions must retain actor and timestamp information.

A future general audit-log capability may consolidate operational audit events, but P1.1 must not rely on an unavailable generic audit system.

## 11. Security Requirements

- Private KYC documents require authenticated controlled delivery.
- No public URL exposure for sensitive identity documents.
- Workspace RLS must be enabled and forced where supported by the existing PostgreSQL security pattern.
- Application authorization remains mandatory even with RLS.
- File metadata and identifiers must not permit cross-workspace access.
- KYC identifiers should be minimized in logs and API responses.

## 12. Deferred

P1.1 does not implement or redefine:

- eSign provider integration
- Aadhaar/identity-provider integration
- automated KYC verification
- background expiry notifications
- WhatsApp/SMS/email delivery
- lease marketplace/leads
- applicant screening engine
- advanced agreement templates
- accounting/GL
- payment gateway/refund changes
- tenant/owner portals

These remain later implementation phases unless separately approved.

## 13. Acceptance Criteria

P1.1 architecture is complete when:

1. Lease is clearly defined as the contractual layer around existing Occupancy.
2. KYC is separated from the existing basic Tenant identity fields.
3. Lease/KYC lifecycle and historical facts are explicit.
4. Workspace isolation, RBAC and RLS requirements are defined.
5. Sensitive KYC storage/access requirements are explicit.
6. Financial authority remains with the locked financial core.
7. Occupancy remains authoritative for space/date/capacity semantics.
8. Renewal, notice, expiry and move-in/out boundaries are defined without inventing competing authorities.
9. Implementation can proceed as model → service → API → tests → CI without architectural ambiguity.

## 14. Decision

**P1.1 ARCHITECTURE LOCKED.**

The implementation direction is an extension of the existing AjnihaStay domain: Lease becomes the contractual layer around Occupancy, while KYC becomes a private, auditable identity/compliance layer around Tenant. Existing occupancy, financial, workspace, RBAC and RLS contracts remain protected.
