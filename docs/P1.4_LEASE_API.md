# P1.4 — Lease API

Status: IMPLEMENTED — CI GATE PENDING

## API boundary

P1.4 exposes the canonical P1.3 Lease Service through authenticated, workspace-scoped REST endpoints. API handlers do not implement Lease mutation business logic themselves.

## Endpoints

- `GET /api/leases/` — workspace-scoped Lease collection.
- `POST /api/leases/create/` — create a draft Lease through `create_lease`.
- `GET /api/leases/<lease_id>/` — workspace-scoped Lease detail.
- `POST /api/leases/<lease_id>/update/` — update P1.3-approved contractual fields through `update_lease`.
- `POST /api/leases/<lease_id>/transition/` — lifecycle transition through `transition_lease`.

## Authorization

Reads require `WorkspaceStaffPermission`. Mutations require `WorkspaceManagerPermission`. Workspace ownership is taken from the authenticated request context and is never accepted as a client-controlled field.

## Validation and errors

Serializer validation handles API-shape validation. Canonical service validation remains authoritative for workspace, occupancy, lifecycle, money, and integrity rules. Invalid service operations return HTTP 400; a missing workspace-scoped Lease detail returns HTTP 404; insufficient permissions return HTTP 403.

## Financial boundary

Lease API operations do not create or mutate Invoice, Payment, PaymentAllocation, AdvanceCredit, FinancialAdjustment, LateFee, Refund, FinalSettlement, or ledger records. Lease rent/deposit remain contractual snapshots until a later explicitly designed financial integration.

## Compatibility

Existing P0.1–P0.12 APIs and contracts are unchanged. Existing Lease OneToOne occupancy semantics remain unchanged; renewal/versioning is deferred to P1.6.

## Regression gate

Dedicated API tests cover create/list/detail/update/transition, authorization, workspace isolation, serializer validation, lifecycle errors, and delegation to the canonical service boundary. P1.4 is locked only after exact-head CI is green across migration graph, migrations, RLS, full Django tests, and system checks.
