# AjnihaStay — P1.6 KYC & Agreement Foundation Specification

**Status:** SPEC LOCK CANDIDATE
**Version:** 1.0
**Date:** 2026-09-14
**Branch:** `phase-p1.5/termination-service`
**Purpose:** Implementation contract for P1.6 without destabilizing validated property, occupancy, leasing, financial, workspace, RBAC, or RLS behavior.

---

## 1. Milestone Definition

P1.6 introduces the **KYC & Agreement Foundation** as a bounded extension of the existing Tenant/Occupancy/Lease architecture.

The milestone solves four problems:

1. Tenant KYC needs an explicit verification lifecycle.
2. Verification decisions need immutable history.
3. Identity documents need lifecycle, expiry tracking, and private authenticated delivery.
4. Tenant contractual/occupancy relationships need a durable agreement linkage foundation.

P1.6 is a foundation milestone. It is **not** a complete KYC provider, eSign, applicant-management, tenant-portal, or agreement-management product.

---

## 2. Architectural Principles

### 2.1 Existing architecture is authoritative

The existing hierarchy remains:

```text
Workspace
  └── Property
       └── Unit
            └── SubUnit
                 └── Occupancy
                      └── Tenant
                           ├── KYC
                           └── Agreement Linkage

Lease remains the contractual layer attached to Occupancy.
```

P1.6 must not make KYC, Agreement, or Tenant a replacement authority for Occupancy or Lease.

### 2.2 Financial boundary

P1.6 must not alter:

```text
Occupancy → Charge → Invoice → Payment
```

No KYC or agreement operation may become a financial state transition.

### 2.3 Service-first mutation

Lifecycle mutations follow:

```text
API → Service → Transaction / lock → Domain state → Immutable history
```

Direct model mutation must not provide an alternative lifecycle path.

### 2.4 Workspace boundary

Every P1.6 tenant-scoped record is workspace-scoped. Workspace membership/RBAC remains the authorization authority and PostgreSQL RLS remains defense-in-depth.

### 2.5 Sensitive document boundary

KYC documents are sensitive identity data. They must not use an unrestricted public-asset delivery model. Public property media and private KYC documents must have separate security semantics.

## 3. Domain Model Contract

### 3.1 KYC Profile

One KYC profile per Tenant.

Conceptual fields:

```text
KycProfile
- id
- tenant (OneToOne)
- workspace
- status
- verified_at
- verified_by
- rejected_at
- rejected_by
- rejection_reason
- created_at
- updated_at
```

Status values:

```text
UNVERIFIED
PENDING
VERIFIED
REJECTED
```

The profile represents the current aggregate verification state. It does not replace the document records or verification history.

### 3.2 KYC Document

A Tenant may have multiple KYC documents.

Conceptual fields:

```text
KycDocument
- id
- tenant
- workspace
- document_type
- document_reference / number (where applicable)
- file / private storage reference
- status
- issued_at (optional)
- expires_at (optional)
- uploaded_by
- uploaded_at
- verified_at (optional)
- verified_by (optional)
- rejected_at (optional)
- rejection_reason (optional)
- created_at
- updated_at
```

Document status:

```text
UPLOADED
UNDER_REVIEW
VERIFIED
REJECTED
EXPIRED
```

Document status is independent from KYC profile status.

Example:

```text
Aadhaar  VERIFIED
PAN      VERIFIED
Passport EXPIRED
```

This must not corrupt the historical verification record.

### 3.3 KYC Verification History

Immutable event/history records are mandatory.

Conceptual fields:

```text
KycVerificationEvent
- id
- workspace
- tenant / kyc_profile
- from_status
- to_status
- actor
- occurred_at
- effective_at (optional)
- reason (optional where transition does not require it)
- metadata
- event_key
- created_at
```

History records cannot be updated or deleted through the normal application contract.

### 3.4 Agreement Linkage

P1.6 introduces linkage, not a full agreement engine.

Conceptual model:

```text
AgreementLink
- id
- workspace
- tenant
- occupancy
- lease (nullable where a future non-lease agreement requires it)
- agreement_type
- reference
- metadata
- created_by
- created_at
```

The linkage must preserve the existing relationship:

```text
Tenant → Occupancy → Lease
```

It must not duplicate contractual truth already owned by Lease/ContractVersion.

## 4. KYC Lifecycle Contract

Allowed transitions:

```text
UNVERIFIED → PENDING
PENDING     → VERIFIED
PENDING     → REJECTED
REJECTED    → PENDING
```

No direct:

```text
UNVERIFIED → VERIFIED
REJECTED   → VERIFIED
VERIFIED   → any non-terminal state
```

is allowed.

`VERIFIED` is terminal for the current verification cycle. A future re-verification workflow may introduce an explicit transition, but P1.6 must not invent one implicitly.

### 4.1 Submit

`UNVERIFIED → PENDING` or `REJECTED → PENDING`.

Submission must validate the tenant/workspace relationship and required document conditions defined by the service contract.

### 4.2 Verify

`PENDING → VERIFIED`.

Verification requires an authorized actor and records immutable history.

### 4.3 Reject

`PENDING → REJECTED`.

A non-empty rejection reason is required and recorded in both current state metadata and immutable history.

### 4.4 Idempotency

Repeating an already-applied identical lifecycle action must be deterministic. It must not create duplicate lifecycle events.

Conflicting repeated actions must return a validation error rather than silently changing historical meaning.

---

## 5. Document Lifecycle Contract

Allowed transitions:

```text
UPLOADED → UNDER_REVIEW
UPLOADED → REJECTED
UNDER_REVIEW → VERIFIED
UNDER_REVIEW → REJECTED
VERIFIED → EXPIRED
```

The service may support an explicit re-upload/replacement operation, but replacing a document must preserve the old record rather than mutate historical identity evidence in place.

An expired document is historical evidence and must not be deleted merely because it expired.

Document verification must not automatically imply Tenant KYC verification unless the KYC service explicitly evaluates the complete required-document policy.

---

## 6. Required Document Policy

P1.6 must avoid hard-coding a universal Indian KYC requirement such as “Aadhaar is always mandatory.”

The initial foundation may define a minimal configurable policy boundary, but provider-specific identity verification is out of scope.

Future property/business workflows may require different document sets.

---

## 7. Private Document Security Contract

### 7.1 Storage

KYC documents must use a private/authenticated storage path or equivalent provider configuration.

They must not be exposed as unrestricted public media assets.

### 7.2 Delivery

Document retrieval must require:

1. authenticated user;
2. active workspace membership;
3. document belongs to the requested workspace;
4. authorization to view sensitive KYC data;
5. controlled delivery rather than exposing a permanent public URL.

### 7.3 Cross-workspace isolation

A valid user in Workspace A must never retrieve a KYC document belonging to Workspace B, even when the document ID is known.

### 7.4 Upload validation

The implementation must validate file type/size according to an explicit allowlist/configuration and must not trust client-provided filenames as a security control.

Executable or otherwise unsafe file content must not become directly executable through document delivery.

### 7.5 Logging

Document access should be observable through the application security/audit layer where available. P1.6 must not log raw document contents or sensitive identity data unnecessarily.

---

## 8. Legacy Tenant KYC Compatibility

Current Tenant contains:

```text
id_proof_type
id_number
id_document
```

These fields are existing API/data compatibility surface and must not be removed or repurposed blindly.

P1.6 implementation must choose an explicit migration strategy:

1. preserve existing fields during rollout;
2. introduce new KYC models/services;
3. migrate/backfill legacy information where safely possible;
4. prevent new sensitive workflows from depending on the legacy public-storage semantics;
5. deprecate legacy fields only in a separately approved contract change.

No destructive migration is permitted in P1.6 without explicit approval.

---

## 9. Agreement Contract

P1.6 AgreementLink is a relationship/indexing foundation.

It may identify:

- agreement type;
- agreement reference;
- tenant;
- occupancy;
- lease;
- associated document/reference metadata.

It must not duplicate:

- Lease lifecycle state;
- Lease dates as a second source of truth;
- ContractVersion history;
- rent/financial state.

If contractual terms change, the existing Lease/ContractVersion lifecycle remains authoritative.

## 10. API Contract

The exact route naming may follow the existing URL conventions, but the functional contract is:

```text
GET  /api/tenants/<tenant_id>/kyc/
POST /api/tenants/<tenant_id>/kyc/submit/
POST /api/tenants/<tenant_id>/kyc/verify/
POST /api/tenants/<tenant_id>/kyc/reject/
GET  /api/tenants/<tenant_id>/kyc/history/

GET  /api/tenants/<tenant_id>/kyc/documents/
POST /api/tenants/<tenant_id>/kyc/documents/
POST /api/kyc/documents/<document_id>/review/
GET  /api/kyc/documents/<document_id>/download/

GET  /api/tenants/<tenant_id>/agreements/
POST /api/tenants/<tenant_id>/agreements/
```

These are a functional contract, not permission to break existing Tenant endpoints.

### 10.1 API rules

- All protected endpoints require authentication.
- Workspace is resolved from the existing request/workspace context.
- Client cannot choose an arbitrary workspace ID to escape isolation.
- Lifecycle status fields are read-only in general serializers.
- Lifecycle actions use dedicated action endpoints/services.
- Unknown lifecycle/action payload fields are rejected where appropriate.
- Error responses must not leak cross-workspace existence.

## 11. Permission Contract

Initial intended permissions:

| Operation | Minimum role |
|---|---|
| View normal tenant KYC metadata | Staff |
| View sensitive KYC documents | Manager |
| Upload/re-upload document | Manager |
| Submit KYC | Manager |
| Verify KYC | Manager |
| Reject KYC | Manager |
| Manage KYC policy/configuration | Admin |
| Manage agreement linkage | Manager |

The implementation must use the existing Membership/RBAC permission architecture. No parallel role system is permitted.

---

## 12. RLS Contract

Every new P1.6 tenant-scoped table must:

```text
- contain workspace_id;
- have PostgreSQL RLS enabled;
- have FORCE RLS enabled where the existing deployment contract requires it;
- enforce workspace USING policy;
- enforce workspace WITH CHECK policy.
```

Tests must cover:

- same-workspace access succeeds;
- cross-workspace read fails;
- cross-workspace create/update fails;
- cross-workspace document delivery fails;
- relationship records cannot join tenants across workspaces.

---

## 13. Immutability / Mutation Boundary Contract

For lifecycle and history models, audit all mutation surfaces:

```text
save()
update()
bulk_update()
bulk_create()
create()
delete()
```

Required behaviour:

- verification history is append-only;
- current KYC status changes only through canonical service;
- verified/rejected audit metadata cannot be casually rewritten;
- historical documents are not overwritten in place when replacement is required;
- agreement linkage mutations use a service boundary where business rules require it.

Raw SQL is outside normal model protections and remains an administrative/database-level responsibility.

---

## 14. Transaction & Concurrency Contract

Lifecycle services must use transactions for state + history changes.

Where concurrent verification/submission/review requests can race, the service must lock the current aggregate row before validating and mutating it.

Invariant:

```text
One accepted state transition
        ↓
One corresponding history event
```

Duplicate concurrent actions must not create duplicate logical transitions.

---

## 15. Adversarial Test Contract

Minimum P1.6 tests:

### KYC state

- valid transitions;
- invalid transitions;
- direct terminal bypass rejection;
- rejection requires reason;
- repeated identical action is idempotent;
- conflicting repeated action rejected;
- verified state cannot be directly downgraded;
- direct `.save()` lifecycle bypass rejected;
- `.update()` lifecycle bypass rejected;
- `.bulk_update()` lifecycle bypass rejected where applicable.

### History

- every accepted transition creates history;
- duplicate action does not duplicate history;
- history is immutable;
- bulk mutation rejected;
- delete protection tested;
- actor/workspace consistency tested.

### Documents

- valid document lifecycle;
- invalid lifecycle;
- expiry handling;
- replacement preserves history;
- file validation;
- unauthorized download rejected;
- cross-workspace download rejected;
- direct public asset access is not the supported contract;
- document status mutation bypass rejected.

### Agreement

- same-workspace linkage succeeds;
- cross-workspace linkage rejected;
- invalid Tenant/Occupancy/Lease relationship rejected;
- Lease remains contractual authority;
- duplicate linkage policy enforced;
- unauthorized mutation rejected.

### Regression

All existing Tenant, Occupancy, Lease, financial, RBAC and RLS tests must remain green.

---

## 16. Migration Contract

Migrations must be additive and reversible in intent.

Initial implementation should:

1. create P1.6 tables;
2. add workspace/RLS policies;
3. preserve existing Tenant columns;
4. optionally backfill KYC metadata only where mapping is deterministic;
5. never fabricate verification history for a legacy record unless the migration can truthfully distinguish the historical event.

A legacy `id_document` must not automatically receive a fabricated `VERIFIED` event.

Legacy data with a document but no known verification decision should remain `UNVERIFIED` or another explicitly defined migration-safe state.

## 17. Non-Goals

P1.6 does not include:

- Aadhaar/PAN external verification;
- DigiLocker;
- third-party KYC providers;
- eSign;
- agreement generation engine;
- agreement template engine;
- applicant portal;
- tenant portal;
- tenant self-service identity verification;
- WhatsApp/SMS KYC workflows;
- AI verification decisions;
- financial changes;
- Lease lifecycle redesign;
- move-in/move-out lifecycle;
- payment gateway integration.

## 19. Final Acceptance Criteria

P1.6 is complete only when all are true:

- KYC has an explicit lifecycle;
- verification history is immutable;
- KYC documents have lifecycle + expiry;
- sensitive documents are privately/authenticated delivered;
- workspace/RLS isolation is verified;
- RBAC uses existing Membership roles;
- agreement linkage does not duplicate Lease authority;
- legacy Tenant API remains compatible;
- no protected financial behaviour changes;
- direct/bulk lifecycle mutation bypasses are closed;
- adversarial tests pass;
- full existing regression suite passes;
- migrations are clean and CI is GREEN.

## 20. Final Architecture Lock

P1.6 adopts:

```text
Tenant
 ├── KycProfile
 │    ├── KycVerificationEvent[]
 │    └── KycDocument[]
 │
 ├── Occupancy
 │     └── Lease
 │          └── ContractVersion[]
 │
 └── AgreementLink[]
```

Authority boundaries:

```text
Tenant       = person/entity identity
Occupancy    = space relationship
Lease        = contractual lifecycle
ContractVersion = contractual-period history
KYC Profile  = current verification aggregate
KYC Event    = immutable verification history
KYC Document = identity evidence
AgreementLink = relationship/index, not contractual truth
```

**P1.6 SPEC LOCK PRINCIPLE:** extend; do not rewrite.

Any implementation decision that conflicts with this document requires an explicit architecture review before code changes.
