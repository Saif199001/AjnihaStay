# P0.12-E — Financial Reporting API

**Status: P0.12-E IMPLEMENTED — CONTRACT LOCK CANDIDATE**

## Purpose

Expose the P0.12 read-only financial reporting and ledger-reconciliation query services through authenticated, workspace-scoped HTTP GET endpoints.

The API is a projection boundary. It does not become a financial authority and does not mutate canonical financial state or the immutable ledger.

## Protected Contracts

P0.1–P0.12-D semantics remain unchanged:

- canonical financial position remains authoritative;
- ledger remains immutable and append-only;
- payments are historical cash receipts;
- allocations and advance-credit applications are settlement, not additional cash;
- only successful refunds reduce recognized cash;
- adjustments and late fees affect receivables, not historical payments;
- final settlement does not fabricate a payment or refund;
- workspace isolation and PostgreSQL RLS remain mandatory;
- reconciliation remains read-only with no automatic repair.

## API Authorization

Every reporting endpoint uses `WorkspaceStaffPermission`.

The workspace is resolved from the existing workspace membership/header contract. A user without active membership cannot access the report. A user cannot select another workspace unless they have an active membership in it.

No reporting endpoint accepts a workspace identifier in the query body as an alternative to the existing request workspace context.

## Endpoints

| Method | Endpoint | Query |
| --- | --- | --- |
| GET | `/api/reports/receivables/` | optional `as_of=YYYY-MM-DD` |
| GET | `/api/reports/invoice/` | required `invoice_id` |
| GET | `/api/reports/invoice-status/` | none |
| GET | `/api/reports/collections/period/` | required `start`, `end` |
| GET | `/api/reports/aging/` | required `as_of` |
| GET | `/api/reports/advance-credits/` | none |
| GET | `/api/reports/adjustments/` | none |
| GET | `/api/reports/late-fees/` | none |
| GET | `/api/reports/ledger/` | optional ISO `start`, `end` datetimes |
| GET | `/api/reports/reconciliation/` | none |

## Date Semantics

- Date-only reporting parameters use ISO `YYYY-MM-DD`.
- Collection period boundaries are inclusive.
- `collections/period` uses `Payment.payment_date` for recorded payments and the successful refund ledger event's occurrence date for refunds.
- Aging uses invoice due date relative to the supplied `as_of` date.
- Future due dates remain in `current`.
- Aging buckets are `current`, `1_30`, `31_60`, `61_90`, and `90_plus`.
- Ledger activity uses inclusive datetime filtering when supplied.

P0.12-E does not invent historical balances by rewinding canonical state. Full historical balance reconstruction remains deferred.

## Numeric / JSON Contract

Money values are serialized as decimal strings with exactly two fractional digits, for example `"12500.00"`.

Dates are ISO strings and datetimes are ISO-8601 strings.

This avoids renderer-dependent floating-point conversion at the reporting API boundary.

## Error Contract

Invalid query dates, missing required query parameters, invalid IDs, or invalid period ordering return HTTP 400 with an `error` message.

A workspace-scoped invoice that does not exist for the requesting workspace returns HTTP 404.

Unsupported HTTP methods return HTTP 405 through the DRF method boundary.

## Read-Only Guarantee

Reporting endpoints call query services only. They do not create, update, delete, allocate, settle, refund, repair, replay, or otherwise mutate financial records.

There is deliberately no automatic reconciliation repair endpoint.

## Reconciliation API

`/api/reports/reconciliation/` exposes the P0.12-D deterministic anomaly report, including missing, orphan, amount-mismatch, relationship-mismatch, and unexpected-event findings.

It is diagnostic only. Findings require an explicit future repair/replay workflow and are never silently modified by reporting.

## Acceptance Criteria

P0.12-E is complete when:

1. all listed reporting surfaces are exposed through GET-only APIs;
2. authorization and workspace isolation are enforced through the existing permission boundary;
3. date/ID validation is deterministic;
4. money serialization is deterministic to two decimal places;
5. reporting remains read-only;
6. dedicated API regression tests are green;
7. the complete Django CI suite, migrations, RLS checks, and system checks are green on the exact final commit;
8. this contract and P0.12 are locked without changing prior financial semantics.

## Deferred

Accounting/GL, GST/tax filing, gateway/bank reconciliation, automatic repair/replay, historical balance reconstruction, exports, materialized reporting infrastructure, forecasting, analytics redesign, and AI remain outside P0.12-E.
