# AjnihaStay — P0.1 Financial State Architecture

**Status:** LOCKED FOR IMPLEMENTATION  
**Phase:** P0 Financial Core  
**Scope:** Financial state architecture only; implementation of the canonical transition service is P0.2.

## 1. Objective

AjnihaStay financial state must have one canonical interpretation and one future canonical mutation authority while preserving validated partial-payment, advance-payment, arrears, allocation, adjustment and workspace-isolation behavior.

The financial domain is represented as:

```text
Occupancy
   ↓
Charge
   ↓
Invoice
   ↓
Settlement Sources
   ├── Payment → PaymentAllocation → Invoice
   └── AdvanceCredit → Application → Invoice
                    
Invoice receivable modifiers:
   └── FinancialAdjustment (debit / credit / discount / waiver / write-off)

Invoice / Settlement
   ↓
Final Settlement
   ↓
Ledger
   ↓
Reporting / Automation
```

## 2. Canonical Financial Truth

For an invoice:

```text
gross_receivable = invoice.total_amount
adjusted_receivable = gross_receivable + debit_adjustments - reducing_adjustments
settlement = payment_allocations + advance_credit_applications
outstanding = max(adjusted_receivable - settlement, 0)
```

Reducing adjustments are credit, discount, waiver and write-off. Debit adjustments increase the receivable.

The persisted `Invoice.paid_amount` and `Invoice.status` are derived state. They are not independent sources of truth and must only be updated by the canonical financial transition path (except controlled migration/rebuild operations).

## 3. Invoice State Machine

The initial supported state machine is intentionally small:

```text
                    settlement > 0
                  ┌───────────────┐
                  ↓               │
PENDING ───────> PARTIAL ───────> PAID
   │                │               │
   └────────────────┴───────────────┘
          when no settlement / full settlement changes
```

### States

- `pending`: no effective settlement against a positive adjusted receivable.
- `partial`: effective settlement exists but adjusted receivable is not fully settled.
- `paid`: adjusted receivable is fully settled.

If receivable is reduced to zero by adjustments, the architecture must not fabricate a payment. The financial position remains derivable from receivable modifiers and settlement records; a future lifecycle extension may introduce an explicit waived/closed state without changing historical settlement facts.

## 4. Financial Event Categories

Every future mutation belongs to one of these categories:

| Category | Source | Financial effect |
|---|---|---|
| Charge | Charge | Increases invoice receivable |
| Invoice | Invoice generation | Creates receivable document |
| Payment | Payment | Creates money-received fact |
| Allocation | PaymentAllocation | Settles a specific invoice |
| Advance credit | AdvanceCredit | Reserves prepaid money |
| Credit application | AdvanceCreditApplication | Settles a specific invoice |
| Debit adjustment | FinancialAdjustment | Increases receivable |
| Credit/discount/waiver/write-off | FinancialAdjustment | Reduces receivable |
| Late fee | Future late-fee domain | Increases receivable |
| Refund | Future refund domain | Reverses/returns received money through an explicit financial event |
| Settlement | Future settlement domain | Closes occupancy-level financial position |

## 5. Money Facts vs Derived State

The architecture distinguishes immutable/historical facts from derived state:

### Historical facts

- Payment amount/date/method/reference
- Payment allocation amount
- Advance credit original amount
- Advance credit application amount
- Financial adjustment amount/type/reason
- Charge amount/date/type
- Invoice billing period and financial terms

These facts must not be silently rewritten after creation.

### Derived state

- Invoice paid amount
- Invoice status
- Invoice outstanding amount
- Payment unallocated amount
- Advance credit available amount
- Occupancy-level outstanding balance
- Dashboard/reporting aggregates

Derived state must be recomputable from canonical financial records.

## 6. Payment Semantics

`Payment.amount` remains the historical amount received. It is not automatically the settlement amount for an invoice.

`PaymentAllocation.amount` is the invoice-specific settlement fact.

Therefore:

```text
Payment.amount ≠ Invoice.settlement necessarily
Payment.amount = Σ allocations + reserved advance credit + unallocated balance
```

A single payment may settle multiple invoices. A payment may also create advance credit for a tenant. Over-allocation is prohibited.

## 7. Advance Credit Semantics

Advance credit represents prepaid money that has not yet been applied to an invoice.

```text
available_credit = original_amount - Σ applications
```

Application against an invoice is a settlement event and must respect:

- same workspace
- same tenant
- available credit
- invoice outstanding amount
- transactional locking

Advance credit must never create a duplicate representation of the original payment principal.

## 8. Adjustment Semantics

Adjustments modify the receivable side, not the historical payment fact.

- `debit`: increases receivable.
- `credit`: reduces receivable.
- `discount`: reduces receivable.
- `waiver`: reduces receivable.
- `write_off`: reduces receivable.

Adjustments are immutable after creation and keyed requests are idempotent within a workspace.

## 9. Settlement Semantics

Invoice settlement is:

```text
payment allocation + advance-credit application
```

Settlement must never be inferred merely from a Payment row that has no allocation.

Occupancy-level final settlement aggregates canonical invoice positions and separately considers security deposit. Security deposit is not silently treated as ordinary invoice payment; future settlement lifecycle work will explicitly model its application/refund/retention outcome.

## 10. Canonical Mutation Authority

The target architecture is:

```text
Business command/event
        ↓
Canonical Financial Transition Service
        ↓
Transactional validation + locking
        ↓
Historical financial fact(s)
        ↓
Recompute derived financial state
        ↓
Ledger event
        ↓
Reporting / automation
```

Future domain services may remain specialized, but all financial state-changing operations must ultimately use the canonical transition authority. Model `save()` methods and signals must not become competing financial state authorities.

P0.2 will introduce the transition service incrementally and preserve current public service/API contracts.

## 11. Transaction and Concurrency Rules

Financial mutations that can affect the same financial aggregate must use transactional locking appropriate to the aggregate:

- invoice mutations lock the invoice before outstanding/state decisions;
- payment allocation locks the payment and affected invoices in deterministic order;
- advance-credit application locks the credit and invoice;
- keyed adjustment operations serialize at workspace scope before idempotency lookup/create;
- recurring billing locks the billing schedule before generation/advance;
- occupancy settlement locks the occupancy and relevant invoices.

No naive database constraint may replace date/capacity-aware occupancy semantics.

## 12. Workspace Boundary

Workspace is the financial tenant boundary. Every financial mutation must verify active workspace membership/authorization and every financial read/mutation must scope related objects to the workspace.

RLS remains defense-in-depth and is not a substitute for domain authorization.

## 13. Protected Existing Behavior

This architecture explicitly preserves:

- partial payments;
- advance billing/payments;
- arrears billing;
- payment allocation semantics;
- advance-credit semantics;
- adjustment idempotency;
- workspace isolation;
- transactional overpayment protection;
- existing API/domain contracts.

No feature in P0 may reinterpret historical payment amounts as invoice settlement without an explicit allocation.

## 14. Future Extensions

The following are deliberately not implemented in P0.1 but must fit this architecture:

- recurring invoice generation;
- proration;
- taxes/GST;
- discounts and configurable credits;
- late fees and grace periods;
- refunds;
- invoice void/cancel and credit/debit notes;
- settlement lifecycle;
- immutable ledger;
- reconciliation;
- accounting/GL;
- financial reporting and analytics.

## 15. P0.1 Acceptance Criteria

P0.1 is complete when:

1. financial truth is explicitly defined;
2. invoice state semantics are explicit;
3. historical facts and derived state are separated;
4. payment vs allocation semantics are explicit;
5. advance credit semantics are explicit;
6. adjustment semantics are explicit;
7. settlement semantics are explicit;
8. concurrency and workspace-boundary rules are explicit;
9. future ledger integration has a defined insertion point;
10. P0.2 can implement the canonical transition service without redesigning these contracts.

**Decision:** This document is the P0.1 architecture contract. Any change to these financial truth rules requires an explicit architecture decision before implementation.
