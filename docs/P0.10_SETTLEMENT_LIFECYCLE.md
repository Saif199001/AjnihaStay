# AjnihaStay — P0.10 Settlement Lifecycle

**Status:** LOCKED FOR IMPLEMENTATION
**Phase:** P0 Financial Core

## Objective

Provide an explicit occupancy-level settlement lifecycle that closes the financial position using canonical invoice receivables and settlement facts, while explicitly handling the security deposit.

## Protected contracts

P0.10 does not reinterpret or mutate historical Payment, PaymentAllocation, AdvanceCredit, AdvanceCreditApplication, FinancialAdjustment, LateFee, or Invoice facts. Existing invoice states remain `pending`, `partial`, and `paid`.

## Canonical settlement position

For every invoice:

`outstanding = max(adjusted_receivable - payment_allocations - advance_credit_applications, 0)`

Occupancy total due is the sum of canonical invoice outstanding amounts.

Security deposit is a separate balance and is never silently counted as invoice payment.

## Settlement outcome

A settlement is eligible when the occupancy has checked out and all canonical invoice outstanding balances are zero.

The settlement records an explicit outcome for the security deposit:

- `full_refund`: entire deposit is refundable.
- `partial_refund`: part of the deposit is refundable and the remainder is retained.
- `full_retention`: entire deposit is retained.
- `no_deposit`: no deposit was collected.

The settlement stores the deposit amount, refundable amount, retained amount, and occupancy-level outstanding amount as historical settlement facts. These amounts are immutable after settlement creation.

No automatic cash refund is created in P0.10. Actual refund processing remains a future explicit financial event.

## Lifecycle rules

1. Settlement is scoped to one workspace and one occupancy.
2. Occupancy must belong to the requested workspace.
3. Occupancy must have a check-out date before settlement.
4. All invoices are locked before eligibility and outcome calculation.
5. The occupancy is locked before the settlement decision.
6. Existing canonical invoice financial positions are used for outstanding balances.
7. Settlement is idempotent per occupancy: an existing settlement is returned rather than duplicated.
8. A settled occupancy cannot receive a second settlement record.
9. Settlement cannot be created while invoice outstanding is positive.
10. Deposit outcome cannot create a payment or alter invoice settlement.
11. Refund/retention accounting is deliberately deferred to future explicit events.

## State

Settlement state is intentionally minimal:

- `settled`: the occupancy financial close has been completed.

No invoice status is changed merely because settlement is recorded.

## Canonical mutation path

`Business command → Canonical Financial Transition Service → transactional occupancy/invoice locking → settlement historical fact → reporting/automation`

## API

P0.10 exposes a manager-authorized POST endpoint to finalize an occupancy settlement. The request supplies only the security-deposit outcome parameters; invoice totals are always derived server-side.

## Concurrency and workspace isolation

Occupancy and all relevant invoices are locked inside one transaction. Workspace authorization is checked before mutation and related records are workspace-scoped. Database uniqueness prevents duplicate settlements.

## Deferred

Actual payment/refund execution, gateway reversals, accounting/GL entries, reconciliation, settlement approval workflow, settlement notes/UI, and ledger postings remain later P0/P3/P4 capabilities.
