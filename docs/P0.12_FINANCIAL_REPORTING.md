# AjnihaStay — P0.12 Financial Reporting Architecture

**Status:** P0.12-A ARCHITECTURE LOCKED
**Phase:** P0 Financial Core
**Scope:** Read-only financial reporting and reconciliation projections. No financial-state mutation.

## 1. Objective

P0.12 introduces the reporting boundary over the canonical financial state and immutable P0.11 financial subledger. Reporting is a read/projection capability and must never become a second financial-state authority.

Target flow:

```text
Canonical Financial State + Immutable Financial Ledger
                    ↓
             Reporting Queries
                    ↓
        Read-only Reporting Projections
                    ↓
 Reports / Aging / Reconciliation / Analytics
```

## 2. Sources of Truth

The reporting layer has two authoritative inputs with distinct responsibilities:

1. **Canonical financial state** — authoritative for current derived balances and lifecycle state, including invoice receivable/outstanding semantics, payment settlement, advance-credit application, adjustments and late fees.
2. **Financial ledger** — authoritative historical record of successfully posted financial events and immutable audit history.

The ledger is not a cached balance table. Reporting must not infer current authoritative balances by mutating or rewriting ledger rows.

## 3. Non-Negotiable Rules

1. P0.12 reporting is read-only.
2. No reporting query may mutate Invoice, Payment, Allocation, AdvanceCredit, Adjustment, LateFee, Refund, FinalSettlement, Occupancy, or ledger state.
3. Existing P0.1–P0.11 contracts remain unchanged.
4. Workspace isolation and RLS remain mandatory on every reporting path.
5. Application authorization remains mandatory; RLS is defense-in-depth.
6. Historical ledger events must never be edited or deleted by reporting code.
7. Payment allocation is settlement linkage, not a second cash receipt.
8. Advance-credit application is not a second cash receipt.
9. Refund cash impact is recognized only for `refund_succeeded`; requested/processing/failed are not cash reversals.
10. Final settlement finalization is a historical snapshot and must not fabricate payment or refund movement.
11. Reporting calculations use explicit date/as-of semantics and must not silently mix event date with creation date.
12. Monetary calculations use Decimal and two-decimal INR precision unless a future currency-aware reporting contract explicitly requires otherwise.
13. Reporting APIs return projections/aggregates, not mutable domain objects as an alternate write surface.
14. Any future materialized reporting projection must be rebuildable from authoritative sources.

## 4. Canonical Reporting Semantics

### Receivable

For an invoice, reporting uses the canonical financial position:

```text
gross_receivable
+ debit_adjustments
- reducing_adjustments
+ late_fees
= adjusted_receivable

settlement
= payment_allocations
+ advance_credit_applications

outstanding
= max(adjusted_receivable - settlement, 0)
```

No report may count the same financial effect twice merely because both a domain fact and its ledger event exist.

### Cash received

Cash received is based on recorded payments, subject to the existing payment/refund semantics. Allocation and advance-credit application do not increase cash received.

### Refunds

Only successful refunds reduce recognized cash. Failed or pending refund lifecycle events remain audit information until a successful reversal exists.

### Advance / prepaid balance

Available advance credit is the existing canonical credit balance after applications. Reporting must not treat the creation of an advance credit as additional cash beyond its source payment.

### Adjustments and late fees

Adjustments and late fees affect receivable reporting, not historical cash received. Their ledger events are historical corroboration, not duplicate amounts to add again to domain totals.

## 5. Reporting Dimensions

P0.12 reporting is designed around these stable dimensions:

- workspace;
- property / unit / sub-unit where applicable;
- occupancy;
- tenant where applicable;
- invoice;
- charge;
- payment;
- payment allocation;
- advance credit/application;
- financial adjustment;
- late fee;
- refund;
- final settlement;
- reporting date / period;
- as-of timestamp.

## 6. Period and As-of Contract

Every financial report that depends on time must make its temporal basis explicit.

### Event-date reports

Use the financial event's authoritative business/effective timestamp or date according to the source domain contract. Ledger `occurred_at` is used for ledger-history reporting.

### Created-date reports

`created_at` is used only when the report explicitly asks when a record was created. It must not silently replace the financial effective date.

### As-of reports

An as-of report answers: **what was knowable/recorded up to the requested cutoff?** It must apply a consistent cutoff to the authoritative source and ledger events and document any source-specific temporal limitation.

### Inclusive periods

Date-range reporting uses inclusive start/end business dates unless a later API contract explicitly defines another convention.

## 7. Core P0.12 Report Families

The architecture reserves these read-only report families:

1. **Receivables** — gross, adjusted, settled and outstanding amounts.
2. **Collections** — recorded payments and successful refunds, without double-counting allocations.
3. **Advance / Prepaid** — created, applied and available advance-credit balances.
4. **Adjustments** — debit/reducing adjustments by type and period.
5. **Late Fees** — generated late fees and overdue exposure.
6. **Invoice Status** — invoice counts and amounts by lifecycle state.
7. **Occupancy Financial Summary** — occupancy-level receivable, settlement and final-settlement projections.
8. **Ledger Activity** — immutable financial event history by event type/source/date.
9. **Reconciliation** — detection of domain facts whose expected ledger event is missing, duplicated or inconsistent.

P0.12-A defines the contract only. Individual report implementations are delivered in later P0.12 stages.

## 8. Reconciliation Boundary

Reconciliation is a read-only integrity projection. It may identify:

- missing expected ledger events;
- duplicate/unexpected ledger events;
- source-reference mismatches;
- amount mismatches where the domain contract supplies a deterministic expected amount;
- workspace/source integrity anomalies.

Reconciliation must not silently repair financial state. Any correction must go through the canonical financial transition authority and, where appropriate, a compensating ledger event.

## 9. Query and Performance Rules

- Reporting queries must be workspace-scoped from the first query boundary.
- Prefer indexed source fields and bounded date ranges.
- Avoid N+1 access across report dimensions.
- Use database aggregation for large aggregate reports where it preserves exact Decimal semantics.
- Do not introduce denormalized reporting tables until query requirements demonstrate a real need.
- If materialized projections are later introduced, define deterministic rebuild and freshness contracts first.

## 10. Authorization

Reporting endpoints remain subject to the existing workspace staff/RBAC model. Read access must not imply mutation capability.

A report must never expose another workspace's financial facts through IDs, filters, joins, exports, reconciliation results, or aggregate leakage.

## 11. API Contract Boundary

P0.12 report APIs are read-only GET/query surfaces unless a later architecture decision explicitly defines another safe reporting operation. They must:

- validate workspace context;
- validate filters/date ranges;
- use canonical reporting services/query functions;
- return deterministic Decimal-safe representations;
- avoid exposing internal mutation methods;
- preserve existing API contracts.

## 12. Rebuildability

Any future cached/materialized reporting projection must be reconstructible from canonical financial state and/or immutable ledger history. The projection itself can never become the sole source of financial truth.

## 13. Explicitly Deferred

P0.12-A does not implement:

- accounting/GL;
- GST accounting treatment;
- tax filing reports;
- payment-gateway reconciliation;
- bank reconciliation;
- exports beyond future report contracts;
- dashboards/UI redesign;
- forecasting;
- AI analytics;
- automated financial-state repair;
- materialized reporting infrastructure without demonstrated need.

## 14. Acceptance Criteria for P0.12-A

P0.12-A is complete when:

1. reporting source-of-truth boundaries are explicit;
2. canonical financial-state and ledger responsibilities are separated;
3. receivable/cash/advance/refund semantics are locked against double counting;
4. period and as-of semantics are explicit;
5. report families are defined;
6. reconciliation is explicitly read-only;
7. workspace/RLS/RBAC requirements are preserved;
8. reporting APIs are defined as read-only projections;
9. rebuildability is required for future cached projections;
10. no existing P0.1–P0.11 financial contract is changed.

**Decision:** P0.12 reporting is an extension of the locked financial architecture. It is a read-only projection layer over canonical financial state and immutable ledger history, never a competing financial-state authority.
