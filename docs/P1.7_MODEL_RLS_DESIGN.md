# AjnihaStay — P1.7 Model & RLS Design

**Status:** DESIGN LOCK CANDIDATE  
**Version:** 1.0  
**Date:** 2026-09-14  
**Branch:** `phase-p1.7/application-workflow-spec`

## 1. Design Authority

P1.7 extends the existing architecture and does not replace validated Tenant, Occupancy, Lease, KYC, financial, Workspace, Membership/RBAC or RLS contracts.

```text
Workspace
  ├── Property → Unit → SubUnit
  │
  ├── Applicant → Application → ApplicationEvent
  │
  └── Tenant → Occupancy → Lease → ContractVersion
```

Application approval is a workflow decision only. It is not tenancy, occupancy, lease or financial truth.

## 2. Applicant Model

Fields:

```text
Applicant
- id
- workspace (FK, PROTECT)
- full_name
- phone
- email (nullable)
- address/profile fields required by P1.7 intake
- created_at
- updated_at
```

Applicant is always workspace-scoped. Phone/email are matching signals, not universal identity keys. No cross-workspace matching or merging is permitted. Identity deduplication is service-controlled and must handle ambiguous matches explicitly.

Applicant deletion is protected while applications reference it so business history remains intact.

## 3. Application Model

Fields:

```text
Application
- id
- workspace (FK, PROTECT)
- applicant (FK, PROTECT)
- property (FK, PROTECT)
- unit (FK, PROTECT, nullable)
- subunit (FK, PROTECT, nullable)
- requested_check_in_date (nullable)
- requested_check_out_date (nullable)
- status
- submitted_at (nullable)
- reviewed_at (nullable)
- decided_at (nullable)
- rejection_reason (nullable)
- withdrawal_reason (nullable)
- created_by (FK user, nullable)
- updated_by (FK user, nullable)
- created_at
- updated_at
```

Status values:

```text
DRAFT
SUBMITTED
UNDER_REVIEW
APPROVED
REJECTED
WITHDRAWN
```

Constraints:
- status is limited to the approved set;
- checkout cannot precede check-in;
- Applicant and Property must share the Application workspace;
- Unit must belong to the selected Property and workspace;
- SubUnit must belong to the selected Unit/Property/workspace;
- invalid relationship combinations are rejected by service/model validation;
- cross-table workspace equality is additionally protected by RLS and adversarial tests.

Property/Unit/SubUnit are requested/preferred inventory only. Applications never reserve capacity.

## 4. Lifecycle Protection

Allowed transitions:

```text
DRAFT        → SUBMITTED
SUBMITTED    → UNDER_REVIEW
SUBMITTED    → WITHDRAWN
UNDER_REVIEW → APPROVED
UNDER_REVIEW → REJECTED
UNDER_REVIEW → WITHDRAWN
```

`APPROVED`, `REJECTED`, and `WITHDRAWN` are terminal.

Status changes must use:

```text
API → Application Service → transaction + select_for_update()
    → validate → mutate → append one ApplicationEvent
```

Normal `.save()`, queryset `.update()` and `.bulk_update()` status changes are blocked. No signal or serializer may become a competing lifecycle authority.

## 5. ApplicationEvent Model

Fields:

```text
ApplicationEvent
- id
- workspace (FK, PROTECT)
- application (FK, PROTECT)
- applicant (FK, PROTECT)
- from_status
- to_status
- actor (FK user, PROTECT)
- occurred_at
- reason (nullable)
- metadata (JSON)
- event_key
- created_at
```

Events are append-only and immutable. Workspace/applicant must match the Application. `event_key` is unique per Application. Canonical `.append()` is the supported creation path. Every accepted transition creates exactly one logical event; deterministic event keys and transaction boundaries make retries safe.

## 6. Duplicate Application Policy

Active statuses:

```text
DRAFT
SUBMITTED
UNDER_REVIEW
```

Initial rule:

```text
same workspace + same applicant + same target property
+ another active application = duplicate
```

Terminal applications remain historical. Unit/subunit preferences must not accidentally weaken the base same-applicant/property active-application rule.

Prefer a PostgreSQL partial unique index if it exactly represents the rule. Otherwise use transactional scope locking plus deterministic `IntegrityError` handling.

## 7. Approval / Tenant Boundary

`UNDER_REVIEW → APPROVED` changes only Application state and history.

It must not implicitly create Tenant, Occupancy, Lease, Charge, Invoice or Payment.

Any future explicit onboarding operation must lock the Application, require APPROVED, deterministically reuse/create the Tenant through the canonical Tenant service, be idempotent, and still leave Occupancy as a separate authoritative operation.

## 8. KYC Boundary

P1.7 does not create another KYC truth. Application may contain workflow-gating metadata if required, but actual verification remains owned by P1.6 `KycProfile` and its canonical services. Application approval is never KYC verification.

## 9. Concurrency

Lifecycle mutations lock the Application row with `select_for_update()` before validation. Active-duplicate creation must be transactionally protected, preferably by a PostgreSQL partial unique index or otherwise by locking the Applicant/target scope. Inventory assignment is separately protected by the existing Occupancy service.

## 10. RLS

Every P1.7 table contains `workspace_id`:

```text
Applicant
Application
ApplicationEvent
```

Each receives PostgreSQL RLS with `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL SECURITY` where required, and both `USING` and `WITH CHECK` policies based on:

```sql
workspace_id = current_setting('app.current_workspace_id', true)::bigint
```

RLS is defense-in-depth; Membership/RBAC remains authorization authority.

## 11. Relationship Isolation

Reject:

```text
Applicant.workspace != Application.workspace
Application.workspace != Property.workspace
Application.unit.property != Application.property
Application.subunit.unit != Application.unit
```

Client input never supplies workspace authority; workspace comes from existing request context.

## 12. Authorization

Reuse existing Membership roles only:

```text
View applications             Staff
Create on behalf of applicant Manager
Review                        Manager
Approve                       Manager
Reject                        Manager
Withdraw on behalf            Manager
Policy/configuration          Admin
```

Inactive membership fails authorization. No parallel application-role system.

## 13. Privacy

Applicant/application data is sensitive workspace data. Serializers expose only required fields. No public applicant endpoints. Do not log unnecessary personal data or documents. P1.7 introduces no applicant scoring or automated adverse decisioning.

## 14. Migration Contract

Additive only:

1. Applicant table;
2. Application table;
3. ApplicationEvent table;
4. indexes/constraints;
5. RLS policies;
6. no destructive Tenant/Occupancy/Lease/KYC/financial changes;
7. no fabricated historical ApplicationEvent records;
8. no automatic Tenant→Applicant conversion.

## 15. Adversarial Coverage

Minimum tests must cover cross-workspace relationships and IDs, property/unit/subunit mismatch, invalid dates, lifecycle bypass via save/update/bulk_update, invalid transitions, terminal mutation, immutable history, duplicate and concurrent creation, concurrent lifecycle actions, inactive membership, RLS USING/WITH CHECK, and proof that approval creates no Tenant/Occupancy/Invoice/Payment side effects.
