# P1.5 Leasing Lifecycle Architecture Contract

**Status: ARCHITECTURE LOCKED**

## 1. Purpose

P1.5 defines the contractual architecture for lease renewal, notice, expiry, termination, cancellation, and lifecycle history. It extends the existing P1.2/P1.3 Lease domain without replacing the existing Occupancy or financial contracts.

## 2. Existing Boundary — LOCKED

The domain remains:

`Property → Unit/SubUnit → Occupancy → Lease`

Occupancy remains the operational relationship to space and period. Lease remains the contractual layer around an Occupancy. Tenant identity remains owned by the Tenant/KYC domain.

The existing P1.2 Lease model, workspace isolation/RLS, RBAC, indexes, validation rules, and P1.3 service lifecycle semantics are preserved unless an explicitly approved P1.5 migration is required by the renewal design.

## 3. Lease and Occupancy Are Separate Lifecycles

Lease lifecycle does not implicitly mutate Occupancy lifecycle.

- Lease termination does not automatically mark Occupancy inactive.
- Lease expiry does not automatically perform move-out.
- Lease renewal does not rewrite Occupancy history.
- Move-out remains an operational Occupancy action and must use its own canonical service.

This prevents contractual and operational state from becoming silently coupled.

## 4. Renewal Architecture

A renewal is a new contractual period/version that preserves the historical lease facts. The original lease must not be overwritten to represent the renewed agreement.

Conceptual lifecycle:

`Lease A → Renewal → Lease B`

Each contractual period must retain its own dates, rent/deposit snapshots, terms, actors, and lifecycle history.

### Relationship decision — LOCKED

The existing `Lease.occupancy` **OneToOne is preserved**. It is a P1.3 operational/contract anchor and must not be converted to a ForeignKey merely to make renewal convenient.

P1.5 represents contractual successors through an immutable `LeaseContractVersion` chain owned by the same Lease anchor:

`Lease (anchor / version 1) → LeaseContractVersion v1 → LeaseContractVersion v2 → ...`

A confirmed `LeaseRenewal` creates exactly one immutable successor `LeaseContractVersion` and stores that successor on `LeaseRenewal.successor_version`. Each successor points to exactly one predecessor. Version numbers are contiguous per Lease and are protected by a database uniqueness constraint.

This is the explicit, migration-safe equivalent of `Lease A → Renewal → Lease B` while preserving the existing Occupancy OneToOne contract. The Lease row remains the canonical lifecycle/authorization anchor; the immutable version chain is the canonical historical contractual-period representation.

### Version invariants

- Version 1 is the immutable snapshot of the original contractual period.
- Existing Lease rows are backfilled to version 1 by migration.
- Confirmed historical renewals are backfilled as successive versions in renewal-number order.
- A renewal confirmation cannot overwrite the predecessor version.
- A confirmed renewal must reference exactly one successor version.
- A successor version must reference the immediately preceding version from the same Lease/workspace.
- Contractual facts on active/expired/terminated/cancelled Lease rows are immutable through the canonical Lease service.
- New contractual terms are represented by a new version, not by editing an effective historical period.
- Contractual periods must not silently overlap unless an explicit future policy permits it.
- Renewal is not a payment, invoice, adjustment, or ledger mutation by itself.
- Any new financial obligations derived from renewal must enter through the existing canonical Financial Core services.

### Renewal confirmation transaction

The canonical confirmation sequence is:

1. Authorize the manager in the resolved workspace.
2. Lock the renewal.
3. Lock the source Lease.
4. Validate the source Lease state and contractual period.
5. Lock the latest contract version for that Lease.
6. Create the next immutable version with the renewal snapshot.
7. Link `LeaseRenewal.successor_version` to the created version.
8. Mark the renewal confirmed.
9. Commit atomically.

The source Lease itself is never rewritten to copy renewal rent, deposit, terms, or dates.

## 5. Lease Lifecycle Semantics

The existing lifecycle remains:

`draft → pending_signature → active → expired`

or

`active → terminated`

and draft/pending-signature may be cancelled.

### Draft

Contract is being prepared and has not become active.

### Pending Signature

Contract is prepared and awaiting the configured signature/approval process. eSign/provider integration remains deferred.

### Active

Contract is currently effective according to its contractual lifecycle. Activation creates the initial immutable contract version when one does not already exist.

### Expired

Contract reached its contractual end without an explicit early termination. Expiry is a controlled lifecycle operation, not an arbitrary direct model write.

### Terminated

An active contract ended before its contractual expiry through an explicit termination action. Termination must preserve actor, timestamp, effective date, and reason through the lifecycle/history design.

### Cancelled

A draft or pending-signature contract was cancelled before becoming active. Cancellation is distinct from termination.

## 6. Notice Architecture

Notice is a separate contractual-process record associated with a Lease/version. `notice_period_days` on Lease remains the contractual rule; it is not itself proof that notice was issued.

A Notice concept must preserve, at minimum:

- notice date;
- effective date;
- notice type/category;
- reason;
- lifecycle status;
- actor;
- creation/update timestamps.

Notice does not directly bypass the Lease Service or write Lease status. A notice may establish the contractual context for a later lifecycle transition.

## 7. Notice vs Termination vs Expiry

These concepts remain distinct:

- **Notice:** contractual/process event communicating an intended effective action.
- **Termination:** explicit early ending of an active lease.
- **Expiry:** natural end at the contractual end date.
- **Cancellation:** withdrawal before activation.

The system must not infer one solely from another unless a later, explicitly locked policy defines that behavior.

Immediate/early termination may exist without a normal notice period where contract/policy permits it; the service must preserve the reason and effective date rather than fabricating a notice.

## 8. Lifecycle History

Lease lifecycle history must be preserved as historical facts rather than relying only on the current Lease row's timestamps.

The P1.5 implementation should use a dedicated immutable lifecycle/history boundary (or an explicitly equivalent append-only representation) for events such as:

- created;
- submitted/pending signature;
- activated;
- renewed;
- notice issued;
- expired;
- terminated;
- cancelled.

History must retain actor, event time, relevant effective date, event type, and safe metadata/reference needed to reconstruct the contractual lifecycle.

Historical records must not be silently rewritten.

## 9. Financial Boundary

Leasing remains outside the financial authority.

Lease may provide contractual inputs such as rent, deposit, dates, and terms, but it must not directly redefine:

- invoice balances;
- payment settlement;
- advance credit;
- adjustments;
- late fees;
- refunds;
- ledger events;
- reporting truth.

Where renewal or termination requires a financial consequence, the operation must delegate to the existing canonical Financial Core services.

## 10. KYC Boundary

KYC remains a separate bounded domain:

`Tenant → KYC Profile → KYC Documents → Verification History`

Lease must not absorb KYC identity/document state. Lease/KYC integration may later enforce required compliance conditions, but each domain remains authoritative for its own state.

## 11. Authorization and Workspace Isolation

All P1.5 mutations must use the established workspace mutation authorization boundary. No client-supplied workspace may override resolved workspace membership.

All records must remain workspace scoped and protected by the existing PostgreSQL RLS/FORCE RLS architecture.

Cross-workspace renewal, notice, history, or lease access must be rejected.

## 12. Service-First Mutation Boundary

The intended flow is:

`API → Lease Lifecycle Service → transactional validation/locking → domain/history mutation → optional canonical Financial Core service`

Direct API model mutation is prohibited.

Concurrency-sensitive operations must lock the relevant workspace/lease/renewal source in a deterministic order and rely on database constraints for final integrity.

## 13. API Direction

API surfaces will be designed only after the P1.5 service/model contract is implemented and tested.

Potential operations include renewal, notice creation, lifecycle history retrieval, expiry, and explicit termination, but exact routes and payloads are not locked by this architecture document.

## 14. Explicitly Deferred

The following are outside P1.5 architecture implementation unless separately approved:

- eSign provider integration;
- Aadhaar/KYC provider integration;
- automated KYC verification;
- WhatsApp/SMS/email notifications;
- payment gateway behavior;
- accounting/GL;
- automated financial repair;
- portal/UI redesign;
- advanced approval workflows.

## 15. Acceptance Criteria

P1.5 implementation may begin only when the following remain true:

1. Renewal preserves original contractual history.
2. Renewal/version representation is explicit and migration-safe.
3. Notice is separate from Lease status.
4. Expiry, termination, and cancellation remain distinct.
5. Lease and Occupancy lifecycles remain separate.
6. Lifecycle history is preserved as historical facts.
7. Financial mutations continue through existing canonical financial services.
8. KYC remains a separate bounded domain.
9. Workspace isolation/RLS and RBAC remain authoritative.
10. Existing P1.2/P1.3 contracts and regression behavior remain protected.
11. No API becomes a competing domain authority.
12. A confirmed renewal has exactly one immutable successor contract version.
13. Effective contractual facts cannot be silently rewritten through the Lease service.

## 16. Decision

**P1.5 Lease Versioning / Successor Architecture is LOCKED.**

The implementation representation is the immutable `LeaseContractVersion` chain under the existing Lease/Occupancy anchor. Production migration/backfill is explicit, renewal confirmation materializes the successor version atomically, and effective Lease contractual fields are frozen through the service boundary.

The next implementation step is lifecycle-history integration, followed by expiry/termination semantics and Notice service design. API expansion remains deferred until those service/model contracts are tested and CI-verified.
