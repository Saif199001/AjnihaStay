# P0.5 — Invoice Lifecycle

## Contract

P0.5 extends the existing invoice lifecycle without changing the persisted status contract.

Existing canonical settlement statuses remain:

- `pending`
- `partial`
- `paid`

`status` remains derived from canonical settlement, not manually assigned by callers.

## Derived lifecycle

An invoice is `overdue` only when:

- canonical outstanding balance is greater than zero, and
- evaluation date is strictly after `due_date`.

Therefore an invoice is not overdue on its due date, and a fully settled invoice is never overdue.

## Financial truth

Lifecycle state is derived from the existing canonical financial position. Historical payments, allocations, advance-credit applications, and financial adjustments are not rewritten by lifecycle evaluation.

The existing partial-payment, advance-credit, arrears, workspace-isolation, authorization, and settlement semantics remain protected.

## Mutation boundary

`refresh_invoice_lifecycle` is registered in the canonical financial transition service. The refresh operation locks the workspace-scoped invoice, recomputes canonical settlement state, and persists only derived `paid_amount` and `status`.

## Explicit non-goals

P0.5 does not introduce new persisted `void` or `cancelled` statuses. Those states require a separate financial lifecycle contract so existing API and settlement semantics are not silently changed.

P0.5 also does not rewrite payment, allocation, advance-credit, or adjustment services. Those contracts remain authoritative and are consumed by the lifecycle calculation.
