# AjnihaStay — P1.7 Applications & Applicant Workflow Specification

**Status:** SPEC LOCK CANDIDATE
**Version:** 1.0
**Date:** 2026-09-14
**Branch:** `phase-p1.7/application-workflow-spec`
**Purpose:** Define the bounded pre-occupancy application workflow without destabilizing validated Tenant, Occupancy, Lease, KYC, financial, Workspace, RBAC, or RLS contracts.

---

## 1. Milestone Definition

P1.7 introduces the **Applications & Applicant Workflow** as a pre-occupancy leasing workflow.

The milestone solves:

1. applicant identity before operational tenancy;
2. application submission against property inventory;
3. review and decision lifecycle;
4. immutable application history;
5. controlled approval-to-Tenant onboarding handoff;
6. workspace/RBAC/RLS isolation and concurrency protection.

P1.7 is not a move-in, Lease, financial, eSign, marketplace, portal, or external-screening milestone.

---

## 2. Core Authority Boundaries

The existing architecture remains authoritative:

```text
Workspace
  ├── Property → Unit → SubUnit
  │
  ├── Applicant → Application[]
  │
  └── Tenant → Occupancy → Lease → ContractVersion
```

Authority:

```text
Applicant          = pre-tenancy applicant identity
Application        = application workflow and decision
ApplicationEvent   = immutable application history
KycProfile         = Tenant KYC verification aggregate
Occupancy          = actual space relationship
Lease              = contractual lifecycle
ContractVersion    = contractual-period history
Financial engine   = Occupancy → Charge → Invoice → Payment
Membership         = workspace authorization
Workspace + RLS    = tenant isolation
```

An Application is never an Occupancy and never a financial record.

---

## 3. Applicant Identity Model

P1.7 introduces an explicit Applicant aggregate so one person can have multiple historical/current applications without prematurely becoming a Tenant.

Conceptual model:

```text
Applicant
- id
- workspace
- full_name
- phone
- email (optional)
- address/profile fields appropriate to application intake
- created_at
- updated_at
```

Applicant is workspace-scoped.

An Applicant may have multiple Applications in the same workspace. Applicant identity must not be duplicated as a new Tenant merely because an application is submitted.

The implementation must use a deterministic identity/deduplication strategy within a workspace. Phone/email may be matching signals but must not be treated as universal global identity keys.

No cross-workspace applicant matching is permitted.

---

## 4. Application Model

Conceptual model:

```text
Application
- id
- workspace
- applicant
- property (required)
- unit (optional)
- subunit (optional)
- requested_check_in_date (optional)
- requested_check_out_date (optional)
- status
- submitted_at
- reviewed_at (optional)
- decided_at (optional)
- rejection_reason (optional)
- withdrawal_reason (optional)
- created_by (optional)
- updated_by (optional)
- created_at
- updated_at
```

Property/unit/subunit references are preferences/requested inventory, not occupancy reservations.

If a unit/subunit is supplied, it must belong to the supplied property and workspace.

An Application must not mutate Unit availability, occupancy, capacity, rent, invoice, payment, or Lease state merely by being submitted or approved.

---

## 5. Application Lifecycle

Initial lifecycle:

```text
DRAFT
  ↓
SUBMITTED
  ↓
UNDER_REVIEW
  ├──→ APPROVED
  ├──→ REJECTED
  └──→ WITHDRAWN
```

Allowed transitions:

```text
DRAFT        → SUBMITTED
SUBMITTED    → UNDER_REVIEW
SUBMITTED    → WITHDRAWN
UNDER_REVIEW → APPROVED
UNDER_REVIEW → REJECTED
UNDER_REVIEW → WITHDRAWN
```

No direct:

```text
DRAFT → APPROVED
SUBMITTED → APPROVED
REJECTED → APPROVED
WITHDRAWN → APPROVED
APPROVED → any non-terminal state
```

`APPROVED`, `REJECTED`, and `WITHDRAWN` are terminal for the current application record.

A future re-application/reopening workflow must use an explicit new application or separately approved transition; P1.7 must not silently reopen terminal records.

---

## 6. Lifecycle Mutation Boundary

Application status changes must follow:

```text
API
 ↓
Application Service
 ↓
transaction + row lock
 ↓
validated state transition
 ↓
ApplicationEvent
```

Direct lifecycle mutation through:

```text
save()
update()
bulk_update()
```

must be blocked where applicable, consistent with existing Lease/KYC lifecycle protection.

Generic serializers must expose status as read-only.

Dedicated action endpoints/services own lifecycle transitions.

---

## 7. Immutable Application History

Every accepted lifecycle transition creates exactly one immutable event.

Conceptual model:

```text
ApplicationEvent
- id
- workspace
- application
- applicant
- from_status
- to_status
- actor
- occurred_at
- reason (optional/required by transition)
- metadata
- event_key
- created_at
```

History is append-only.

Events cannot be edited or deleted through the normal application contract.

Each accepted transition must have one corresponding logical history event.

Repeated identical actions must be deterministic and must not create duplicate logical events.

---

## 8. Submission Rules

Submission must validate:

1. applicant belongs to the same workspace;
2. property belongs to the same workspace;
3. optional unit belongs to that property/workspace;
4. optional subunit belongs to that unit/property/workspace;
5. requested dates are internally valid;
6. application is in a submit-capable state;
7. required application fields/policy are satisfied.

Submitting an application does not reserve inventory.

---

## 9. Review / Decision Rules

Only authorized active workspace members may review or decide an application.

Initial permission contract:

| Operation | Minimum role |
|---|---|
| View application metadata | Staff |
| Create application on behalf of applicant | Manager |
| Review application | Manager |
| Approve application | Manager |
| Reject application | Manager |
| Withdraw application on behalf of applicant | Manager |
| Manage application policy/configuration | Admin |

No parallel role system is permitted.

Reject requires a non-empty reason.

Withdraw should preserve a reason where the actor is withdrawing on behalf of an applicant.

Decision operations must not directly create financial records.

---

## 10. Approval → Tenant Boundary

Approval means:

```text
Application = APPROVED
```

It does **not** automatically mean:

```text
Tenant created
Occupancy created
Lease created
Invoice created
Payment created
```

P1.7 must provide a controlled onboarding handoff contract so a future move-in workflow can create/link a Tenant without duplicating identity or bypassing Tenant/Occupancy/Lease services.

If an explicit P1.7 onboarding operation creates a Tenant, it must be idempotent and must never create Occupancy or financial state as an implicit side effect.

Actual space assignment remains the responsibility of the authoritative Occupancy service.

---

## 11. KYC Boundary

P1.7 may record application-level KYC requirement/status metadata only where necessary for workflow gating.

It must not duplicate KYC verification truth.

When a real Tenant exists, KYC verification remains owned by `KycProfile` and its canonical services.

P1.7 does not introduce external Aadhaar/PAN verification, DigiLocker, third-party KYC, or applicant self-service verification.

Application approval must not be represented as KYC verification.

A future policy may require verified KYC before onboarding, but such gating must be explicit and configurable rather than hard-coded to one document type.

---

## 12. Inventory / Availability Boundary

Applications may target:

```text
Property
Unit
SubUnit
```

but these references represent requested/preferred inventory only.

They do not reserve capacity.

The authoritative occupancy operation must re-check current inventory, dates, capacity, unit/subunit activity, workspace ownership, and all existing occupancy constraints at the time of actual assignment.

Two approved applications may therefore exist for the same requested inventory; only the authoritative Occupancy operation determines whether actual assignment succeeds.

---

## 13. Duplicate Application Policy

The system must prevent accidental duplicate active applications without preventing legitimate historical or multi-property applications.

Initial rule:

```text
Same workspace
+ same applicant
+ same target property
+ same active application
= duplicate rejected
```

For unit/subunit-specific applications, the target inventory may further distinguish legitimate applications.

Historical terminal applications remain preserved.

A unique database constraint should be used only where it exactly represents the approved logical duplicate rule; otherwise service-level validation plus concurrency locking must enforce it.

Cross-workspace matches are never considered duplicates.

---

## 14. Concurrency Contract

Application lifecycle mutations must lock the application row before validating and mutating status.

Applicant/application creation and active-duplicate checks must use transactional protection appropriate to the chosen database constraints.

Approval must be safe under concurrent requests:

```text
Only one valid transition from UNDER_REVIEW may win.
```

Inventory assignment is separately concurrency-controlled by the existing Occupancy service.

Application approval must not bypass those occupancy locks/validations.

---

## 15. Workspace / RLS Contract

Every P1.7 tenant-scoped table must:

```text
- contain workspace_id;
- use PostgreSQL RLS;
- use FORCE RLS where deployment contract requires it;
- enforce USING workspace policy;
- enforce WITH CHECK workspace policy.
```

Tests must cover:

- same-workspace read/write;
- cross-workspace read rejection;
- cross-workspace create/update rejection;
- guessed application IDs;
- mismatched Applicant/Application workspace;
- mismatched Property/Unit/SubUnit workspace;
- inactive membership;
- unauthorized lifecycle actions.

Client payload must never choose an arbitrary workspace to escape isolation.

---

## 16. API Contract

Functional contract:

```text
GET  /api/applicants/
POST /api/applicants/
GET  /api/applicants/<applicant_id>/

GET  /api/applications/
POST /api/applications/
GET  /api/applications/<application_id>/

POST /api/applications/<application_id>/submit/
POST /api/applications/<application_id>/review/
POST /api/applications/<application_id>/approve/
POST /api/applications/<application_id>/reject/
POST /api/applications/<application_id>/withdraw/
GET  /api/applications/<application_id>/history/
```

Exact URL style may follow existing project conventions, but the functional boundaries above must remain.

API rules:

- protected endpoints require authentication;
- workspace comes from existing request context;
- status is read-only in general serializers;
- lifecycle actions use dedicated services;
- unknown action/status fields are rejected where appropriate;
- cross-workspace errors must not leak object existence;
- bounded pagination is required for list/history endpoints.

No applicant public portal is part of P1.7.

---

## 17. Security / Privacy

Applicant data may contain personal information and must be treated as sensitive workspace data.

Requirements:

- no public applicant endpoints;
- workspace-aware authorization on every query;
- no arbitrary object-ID access;
- no sensitive data in logs unnecessarily;
- no cross-workspace enumeration;
- no client-controlled workspace authority;
- application history protected by the same workspace/RBAC boundary;
- document handling must reuse the approved P1.6 private-storage security boundary where applicable.

No applicant scoring or automated adverse decisioning is introduced in P1.7.

---

## 18. Financial / Lease Isolation

P1.7 must not modify:

```text
Occupancy → Charge → Invoice → Payment
```

and must not mutate:

- Lease status;
- ContractVersion;
- rent authority;
- security-deposit financial state;
- invoice/payment state.

If future onboarding creates an Occupancy, that must be a separate explicit operation through the canonical Occupancy service.

Application approval itself is not a financial transition.

---

## 19. Migration Contract

Migrations must be additive.

They must:

1. create Applicant/Application/ApplicationEvent tables;
2. add workspace/RLS policies;
3. preserve existing Tenant/Occupancy/Lease/KYC tables and fields;
4. avoid destructive backfills;
5. avoid fabricated application history;
6. avoid changes to financial lifecycle schema.

No existing Tenant should be converted into an Applicant automatically unless a deterministic, explicitly approved migration is later defined.

---

## 20. Adversarial Test Contract

Minimum P1.7 coverage:

### Applicant

- workspace isolation;
- active membership;
- duplicate identity policy;
- cross-workspace lookup;
- unauthorized access;
- safe personal-data serialization.

### Application lifecycle

- every valid transition;
- every invalid transition;
- direct status `.save()` bypass;
- queryset `.update()` bypass;
- bulk update bypass;
- duplicate transition idempotency;
- conflicting transition rejection;
- rejection reason required;
- withdrawal semantics;
- terminal state protection.

### History

- one event per accepted transition;
- duplicate action does not duplicate logical history;
- immutable events;
- delete protection;
- actor/workspace consistency;
- cross-workspace isolation.

### Inventory relationship

- property/unit mismatch rejected;
- unit/subunit mismatch rejected;
- cross-workspace inventory rejected;
- application does not reserve occupancy;
- approved applications do not bypass occupancy capacity checks.

### Approval/onboarding

- approval does not create financial records;
- approval does not silently create occupancy;
- controlled Tenant handoff is idempotent if implemented;
- applicant identity is not duplicated unnecessarily;
- future KYC gate cannot fabricate verification.

### Security

- anonymous access rejected;
- inactive membership rejected;
- guessed IDs rejected safely;
- cross-workspace object access rejected without existence leakage;
- unknown payload fields rejected where appropriate;
- bounded pagination;
- sensitive fields not unnecessarily exposed.

### Regression

All existing Tenant, Occupancy, Lease, KYC, financial, RBAC, RLS and API regression tests must remain green.

## 23. Acceptance Criteria

P1.7 is complete only when:

- Applicant is a distinct pre-Tenant identity aggregate;
- Application has explicit lifecycle;
- lifecycle mutation has one canonical service authority;
- application history is immutable;
- duplicate active applications are controlled;
- property/unit/subunit references are workspace-safe;
- applications do not reserve occupancy;
- approval does not mutate financial state;
- Tenant onboarding handoff is explicit and idempotent where implemented;
- KYC remains authoritative in P1.6;
- Workspace/RBAC/RLS isolation is verified;
- adversarial tests pass;
- existing regression suite remains green;
- migrations are clean;
- CI is GREEN.

## 24. Architecture Lock Principle

P1.7 extends the existing product rather than rewriting it.

The critical boundary is:

```text
Applicant
   ↓
Application
   ↓
Review / Decision
   ↓
Approved
   ↓
Explicit onboarding handoff
   ↓
Tenant
   ↓
Occupancy
   ↓
Lease
   ↓
Financial lifecycle
```

No step may silently assume the authority of the next domain.

**P1.7 SPEC LOCK PRINCIPLE: Applicant workflow is pre-occupancy workflow; approval is not tenancy, occupancy, lease, or financial truth.**
