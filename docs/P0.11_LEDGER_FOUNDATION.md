# AjnihaStay — P0.11 Ledger Foundation

**Status:** P0.11 COMPLETE / LOCKED  
**Phase:** P0 Financial Core  
**Scope:** Immutable financial subledger foundation. Accounting/GL remains a later capability.

## 1. Objective

AjnihaStay needs an immutable financial history that can be rebuilt independently from mutable/derived financial state and can later feed reconciliation, reporting, automation, and accounting/GL.

P0.11 introduces a **financial subledger**, not a general-ledger/accounting chart of accounts. It records canonical financial events after successful domain mutations without changing existing financial semantics.

Target flow:

```text
Business command/event
        ↓
Canonical Financial Transition
        ↓
Transactional domain mutation
        ↓
Immutable Financial Ledger Event
        ↓
Reporting / Reconciliation / Automation
        ↓
Future Accounting / GL projection
```

## 2. Non-Negotiable Rules

1. The ledger is append-only at both application and PostgreSQL database layers.
2. Ledger rows are immutable financial history; UPDATE and DELETE are prohibited.
3. Ledger creation must never become a second financial-state authority.
4. Existing Invoice, Payment, PaymentAllocation, AdvanceCredit, AdvanceCreditApplication, FinancialAdjustment, LateFee, Refund, and FinalSettlement contracts remain unchanged.
5. A ledger event represents a successful canonical financial fact or state-changing financial event; failed/rolled-back mutations must not leave ledger rows.
6. Ledger writes occur in the same database transaction as the authoritative financial mutation wherever the mutation is transactional.
7. Ledger entries are workspace-scoped and protected by application authorization plus PostgreSQL RLS defense-in-depth.
8. Ledger records must be sufficient to identify the originating financial event without copying mutable business state as an alternate source of truth.
9. Derived balances are never stored in the ledger as if they were historical money movement.
10. Accounting/GL account mapping is explicitly deferred from P0.11.

## 3. Locked Event Vocabulary

P0.11 uses a financial event subledger. The following event types are the locked vocabulary:

| Event | Historical source | Ledger meaning | Cash movement? |
|---|---|---|---|
| `invoice_created` | Invoice | Receivable created | No |
| `payment_recorded` | Payment | Money received | Yes |
| `payment_allocated` | PaymentAllocation | Payment applied to invoice | No; settlement linkage |
| `advance_credit_created` | AdvanceCredit | Prepaid balance reserved | No; source payment is the cash receipt |
| `advance_credit_applied` | AdvanceCreditApplication | Prepaid balance applied | No |
| `adjustment_created` | FinancialAdjustment | Receivable changed | No |
| `charge_generated` | Charge | Receivable-side charge fact | No |
| `recurring_invoice_generated` | Recurring Invoice + Charge | Recurring receivable cycle created | No |
| `late_fee_generated` | LateFee | Receivable increased by late fee | No |
| `refund_requested` | PaymentRefund | Refund lifecycle request | No |
| `refund_processing` | PaymentRefund | Refund lifecycle processing state | No |
| `refund_succeeded` | PaymentRefund | Successful money reversal | Yes |
| `refund_failed` | PaymentRefund | Failed refund attempt | No |
| `final_settlement_finalized` | FinalSettlement | Occupancy financial snapshot finalized | No; does not fabricate refund/payment |

`invoice_lifecycle_refreshed` is deliberately **not** a ledger event. Lifecycle refresh reconciles derived state and does not create a new financial fact.

The event vocabulary may be extended only through an explicit architecture decision.

## 4. Event-Key Contract

Ledger event keys are deterministic and unique within a workspace:

| Event | Key pattern |
|---|---|
| `invoice_created` | `invoice:{invoice_id}:created` |
| `payment_recorded` | `payment:{payment_id}:recorded` |
| `payment_allocated` | `payment-allocation:{allocation_id}:created` |
| `advance_credit_created` | `advance-credit:{credit_id}:created` |
| `advance_credit_applied` | `advance-credit-application:{application_id}:created` |
| `adjustment_created` | `adjustment:{adjustment_id}:created` |
| `charge_generated` | `charge:{charge_id}:generated` |
| `recurring_invoice_generated` | `recurring-invoice:{invoice_id}:generated` |
| `late_fee_generated` | `late-fee:{late_fee_id}:generated` |
| `refund_requested` | `refund:{refund_id}:requested` |
| `refund_processing` | `refund:{refund_id}:processing` |
| `refund_succeeded` | `refund:{refund_id}:succeeded` |
| `refund_failed` | `refund:{refund_id}:failed` |
| `final_settlement_finalized` | `final-settlement:{settlement_id}:finalized` |

The database uniqueness boundary is `workspace + event_key`.

## 5. Money Semantics

The ledger must distinguish **receivable effects** from **cash/prepaid effects** and must not double-count them.

```text
Invoice creation      → receivable +1000
Payment received      → cash +1000
Payment allocation    → settlement linkage; not another cash receipt
Advance credit create → prepaid balance reserved; source payment is the cash receipt
Advance credit apply  → consumes prepaid balance; not another cash receipt
Credit adjustment     → receivable -100
Debit adjustment      → receivable +100
Charge generated      → receivable +charge
Late fee              → receivable +fee
Refund succeeded      → cash returned -refund
Final settlement      → historical snapshot finalization; no fabricated cash
```

These are financial-subledger effects, not final accounting debits/credits. Exact GL account selection is deferred.

## 6. Ledger Record Contract

The ledger record contains:

- workspace;
- immutable event type;
- immutable amount with two-decimal monetary precision;
- immutable event date/time;
- immutable creation timestamp;
- source financial references where applicable;
- actor/user where available;
- stable event key;
- structured metadata required for audit/rebuild, without duplicating mutable business state.

Source references are PROTECT relationships. Ledger history must not be orphaned by deletion of source financial facts.

### Source relationship integrity

When multiple source references are supplied, the canonical model boundary validates that:

- invoice and occupancy refer to the same occupancy;
- payment and invoice agree when the payment is invoice-linked;
- payment and occupancy agree when the payment is invoice-linked;
- all supplied references belong to the ledger workspace.

An unlinked payment may legitimately be paired with an occupancy only where the originating domain operation provides that context (for example, advance-credit creation).

## 7. Immutability / Append-Only Enforcement

After creation, these facts cannot change:

- workspace;
- event type;
- amount;
- event timestamp;
- creation timestamp;
- source identity;
- financial references;
- actor;
- event key;
- metadata.

Two layers enforce this:

1. Django model save-path validation prevents normal object mutation.
2. PostgreSQL trigger protection rejects all UPDATE and DELETE operations on the ledger table.

Corrections are represented by a new compensating financial event through the canonical financial transition authority. Existing ledger rows are never edited in place.

## 8. Transaction Boundary

For transactional financial mutations:

```text
atomic transaction
  ├─ lock/validate canonical aggregate
  ├─ create/update authoritative domain facts
  ├─ recompute derived state
  └─ append ledger event
commit
```

If any step fails, the entire transaction rolls back.

Ledger posting must not independently mutate Invoice.paid_amount, Invoice.status, Payment.amount, AdvanceCredit.original_amount, or any other authoritative/derived financial state.

## 9. Existing Contract Preservation

P0.11 does **not** change:

- partial-payment behavior;
- payment allocation behavior;
- advance-credit behavior;
- arrears behavior;
- adjustment behavior/idempotency;
- late-fee calculation;
- refund state machine;
- final-settlement eligibility/outcomes;
- workspace authorization/RLS;
- existing API contracts;
- canonical financial transition names already implemented.

Ledger integration is an extension point around these contracts, not a replacement for them.

## 10. Refund Semantics

- `refund_requested` is a lifecycle request, not cash movement.
- `refund_processing` is a lifecycle state, not cash movement.
- `refund_succeeded` represents the actual successful financial reversal.
- `refund_failed` is an audit/lifecycle event and must not reduce recognized cash.

Provider execution remains deferred/provider-neutral unless already implemented by the existing refund domain.

## 11. Recurring Invoice Semantics

A recurring billing cycle produces a specialized `recurring_invoice_generated` event plus its underlying `charge_generated` event.

`recurring_invoice_generated` is the canonical invoice-creation event for the recurring cycle. It is **not** an additional cash movement and must not be counted as a second receivable or cash receipt merely because a charge event also exists.

A generic `invoice_created` event is intentionally not emitted for the same recurring invoice.

## 12. Final Settlement Semantics

`FinalSettlement` is a historical occupancy-level snapshot. Its ledger event records finalization and outcome, but does not fabricate payment/refund cash movement.

Security-deposit refund becomes a cash-reversal ledger event only when an actual refund financial fact exists in the future settlement/refund integration.

## 13. Idempotency and Concurrency

Ledger posting is idempotent.

A repeated post of the same workspace/event key with the same effect returns the existing ledger record. Reuse of an existing event key for a different effect fails deterministically.

The database uniqueness constraint is the final race-safe guard; application logic handles replay/conflict semantics. Domain-operation idempotency remains a separate concern and is not replaced by ledger idempotency.

Source aggregate locking remains owned by the canonical domain service.

## 14. Workspace Isolation

- source objects must be workspace-valid before posting;
- event-key uniqueness is workspace-scoped;
- ledger source references must be workspace-consistent;
- PostgreSQL RLS is defense-in-depth and does not replace application authorization;
- PostgreSQL FORCE RLS remains enabled for the ledger table.

## 15. Rebuild and Audit Goal

The subledger must support future capabilities to:

- reconstruct financial event history;
- detect missing or duplicated postings;
- reconcile domain facts against ledger events;
- build reporting projections;
- feed automation;
- project into a future accounting/GL layer.

The ledger is a historical event record, not a cached balance table.
