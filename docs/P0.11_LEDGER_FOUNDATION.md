# AjnihaStay — P0.11 Ledger Foundation

**Status:** LOCKED FOR IMPLEMENTATION  
**Phase:** P0 Financial Core  
**Scope:** Immutable financial subledger foundation. Accounting/GL remains a later capability.

## 1. Objective

AjnihaStay needs an immutable financial history that can be rebuilt independently from mutable/derived financial state and can later feed reconciliation, reporting, automation, and accounting/GL.

P0.11 introduces a **financial subledger**, not a general-ledger/accounting chart of accounts. It records canonical financial events after successful domain mutations without changing existing financial semantics.

Target flow:

```text
Business command/event
        ↓
Canonical Financial Transition
        ↓
Transactional domain mutation
        ↓
Immutable Financial Ledger Event
        ↓
Reporting / Reconciliation / Automation
        ↓
Future Accounting / GL projection
```

## 2. Non-Negotiable Rules

1. The ledger is append-only.
2. Ledger rows are immutable financial history; no update/delete lifecycle is permitted.
3. Ledger creation must never become a second financial-state authority.
4. Existing Invoice, Payment, PaymentAllocation, AdvanceCredit, AdvanceCreditApplication, FinancialAdjustment, LateFee, Refund, and FinalSettlement contracts remain unchanged.
5. A ledger event represents a successful canonical financial fact or state-changing financial event; failed/rolled-back mutations must not leave ledger rows.
6. Ledger writes occur in the same database transaction as the authoritative financial mutation wherever the mutation is transactional.
7. Ledger entries are workspace-scoped and protected by application authorization plus PostgreSQL RLS defense-in-depth.
8. Ledger records must be sufficient to identify the originating financial event without copying mutable business state as an alternate source of truth.
9. Derived balances are never stored in the ledger as if they were historical money movement.
10. Accounting/GL account mapping is explicitly deferred from P0.11.

## 3. Ledger Granularity

P0.11 uses a **financial event subledger**. One canonical business event produces one immutable ledger event representing its financial effect.

Initial event categories:

| Event | Historical source | Ledger meaning |
|---|---|---|
| `invoice_created` | Invoice | Receivable created |
| `payment_recorded` | Payment | Money received |
| `payment_allocated` | PaymentAllocation | Payment applied to invoice |
| `advance_credit_created` | AdvanceCredit | Prepaid balance reserved |
| `advance_credit_applied` | AdvanceCreditApplication | Prepaid balance applied |
| `adjustment_created` | FinancialAdjustment | Receivable changed by adjustment |
| `late_fee_created` | LateFee | Receivable increased by late fee |
| `refund_requested` | PaymentRefund | Refund obligation/event requested |
| `refund_succeeded` | PaymentRefund | Money returned after successful refund |
| `refund_failed` | PaymentRefund | Refund attempt failed; no cash reversal is recognized |
| `final_settlement` | FinalSettlement | Occupancy financial position finalized |

The event vocabulary may be extended only through an explicit architecture decision.

## 4. Money Semantics

The ledger must distinguish **receivable effects** from **cash/prepaid effects** and must not double-count them.

Examples:

```text
Invoice creation      → receivable +1000
Payment received      → cash +1000
Payment allocation    → settlement linkage; not another cash receipt
Advance credit create → prepaid liability/credit balance +500; source payment is the cash receipt
Advance credit apply  → consumes prepaid balance; not another cash receipt
Credit adjustment     → receivable -100
Debit adjustment      → receivable +100
Late fee              → receivable +fee
Refund succeeded      → cash returned -refund
```

These are financial-subledger effects, not final accounting debits/credits. Exact GL account selection is deferred.

## 5. Ledger Record Contract

The ledger record should contain:

- workspace;
- immutable event type;
- immutable amount with two-decimal monetary precision;
- event date/time;
- source object type and source object identifier;
- optional invoice, payment, occupancy and tenant references where applicable;
- actor/user where available;
- stable idempotency/event key;
- structured metadata required for audit/rebuild, without duplicating mutable business state.

Source references are PROTECT relationships where practical. The ledger must not be orphaned by deletion of a source financial fact.

## 6. Idempotency

Ledger posting must be idempotent.

The uniqueness boundary is:

```text
workspace + event_key
```

A repeated post of the same canonical event returns the existing ledger record. Reuse of an existing event key for a different financial source/effect is a conflict and must fail safely.

The database uniqueness constraint is the final race-safe guard; application logic handles replay/conflict semantics.

## 7. Immutability

After creation, these facts cannot change:

- workspace;
- event type;
- amount;
- event timestamp/date;
- source identity;
- financial references;
- actor;
- event key;
- metadata.

No normal service may update or delete a ledger record. Corrections are represented by a new compensating financial event through the canonical transition authority.

## 8. Transaction Boundary

For transactional financial mutations:

```text
atomic transaction
  ├─ lock/validate canonical aggregate
  ├─ create/update authoritative domain facts
  ├─ recompute derived state
  └─ append ledger event
commit
```

If any step fails, the entire transaction rolls back.

Ledger posting must not independently mutate Invoice.paid_amount, Invoice.status, Payment.amount, AdvanceCredit.original_amount, or any other authoritative/derived financial state.

## 9. Existing Contract Preservation

P0.11 does **not** change:

- partial-payment behavior;
- payment allocation behavior;
- advance-credit behavior;
- arrears behavior;
- adjustment behavior/idempotency;
- late-fee calculation;
- refund state machine;
- final-settlement eligibility/outcomes;
- workspace authorization/RLS;
- existing API contracts;
- canonical transition names already implemented.

Ledger integration is an extension point around these contracts, not a replacement for them.

## 10. Refund Semantics

Refund requests and outcomes require care because a requested/processing refund is not cash movement.

Therefore:

- `refund_requested` records an explicit refund lifecycle event if posted by the canonical transition;
- `refund_succeeded` represents the actual financial reversal;
- `refund_failed` is an audit/lifecycle event and must not reduce recognized cash.

Provider execution remains deferred/provider-neutral unless already implemented by the existing refund domain.

## 11. Final Settlement Semantics

`FinalSettlement` is a historical occupancy-level snapshot. Its ledger event records the finalization event and outcome, but does not fabricate payment/refund cash movement.

Security-deposit refund becomes a cash-reversal ledger event only when an actual refund financial fact exists in the future settlement/refund integration.

## 12. Rebuild and Audit Goal

The subledger must support future capabilities to:

- reconstruct financial event history;
- detect missing or duplicated postings;
- reconcile domain facts against ledger events;
- build reporting projections;
- feed automation;
- project into a future accounting/GL layer.

The ledger is therefore a historical event record, not a cached balance table.

## 13. Concurrency and Workspace Isolation

Ledger posting follows the same workspace boundary as the source event.

- source objects must be workspace-valid before posting;
- event-key uniqueness is workspace-scoped;
- source aggregate locking remains owned by the canonical domain service;
- ledger insertion must be race-safe through database constraints;
- PostgreSQL RLS is defense-in-depth and does not replace application authorization.

## 14. P0.11 Acceptance Criteria

P0.11 is complete when:

1. an immutable financial subledger model exists;
2. event types and source semantics are explicit;
3. event-key idempotency is database-enforced;
4. ledger records are workspace isolated with RLS;
5. ledger records cannot be edited/deleted through the normal model/service path;
6. canonical financial mutations can append ledger events transactionally;
7. replay/conflict behavior is deterministic;
8. ledger posting cannot mutate authoritative financial state;
9. regression tests prove existing financial contracts remain unchanged;
10. the foundation is ready for reconciliation/reporting and later GL projection.

**Decision:** P0.11 is an extension of the locked P0 financial architecture. It does not introduce a competing financial-state authority or accounting/GL implementation.
