# P1.6 Private Storage & Security Design

**Status:** DESIGN LOCK CANDIDATE  
**Version:** 1.0  
**Date:** 2026-09-14  
**Milestone:** P1.6 KYC & Agreement Foundation  
**Branch:** `phase-p1.5/termination-service`

## 1. Purpose

This document locks the storage/security boundary for sensitive KYC documents before P1.6 model migration and API implementation.

KYC documents are sensitive personal records. They must not inherit the application's current generic media semantics merely because the project currently uses Cloudinary as its global file storage.

The design therefore separates:

`KycDocument metadata → private storage key → storage adapter → controlled authenticated delivery`

The KYC domain owns authorization and lifecycle state. The storage provider must never become the source of truth for workspace authorization, KYC status, verification, or document ownership.

## 2. Current-State Finding

AjnihaStay currently configures `cloudinary_storage.storage.MediaCloudinaryStorage` as `DEFAULT_FILE_STORAGE`. Tenant also has a legacy `id_document` FileField using `tenant_documents/`.

This is acceptable as legacy compatibility, but it is **not** sufficient as the P1.6 security contract. New KYC documents must use an explicit private-storage boundary rather than exposing a generic model file URL.

No destructive migration of the legacy Tenant KYC fields is permitted in P1.6.

## 3. Locked Security Principles

1. **Private by default.** Every new KYC document is stored as a private object/resource.
2. **No public KYC URLs.** `KycDocument.file`/storage key must never be rendered as a public media URL by serializers.
3. **Authorization before delivery.** Authentication, active workspace membership, workspace ownership, document ownership, and sensitive-document permission are checked before any document is released.
4. **Application authorization is canonical.** Cloudinary/storage ACLs are defense-in-depth, not the tenant-isolation authority.
5. **Provider abstraction.** KYC services depend on an adapter interface, not directly on Cloudinary SDK calls.
6. **Opaque storage keys.** Keys must not contain tenant names, phone numbers, government ID numbers, or other PII.
7. **No sensitive logging.** File contents, document numbers, raw storage URLs, signatures, and authorization tokens must not enter application logs.
8. **Controlled delivery.** The API returns a short-lived controlled response or short-lived provider URL only after authorization succeeds.
9. **Replacement is additive.** Re-upload/replacement creates a new KycDocument record; old records remain auditable and are not silently overwritten.
10. **Lifecycle is authoritative in the database.** Storage deletion/availability must not change KYC verification truth.

## 4. Storage Adapter Boundary

Introduce a small provider-neutral adapter, conceptually:

```text
PrivateDocumentStorage
  put(file, *, storage_key, content_type) -> StorageObject
  open(storage_key) -> readable object
  delete(storage_key) -> None
  exists(storage_key) -> bool
  create_controlled_access(storage_key, *, expires_at) -> DeliveryGrant
```

The exact Python names may differ during implementation, but the boundary must preserve these responsibilities.

### Adapter responsibilities

- validate provider configuration;
- upload bytes to a private namespace/resource type;
- return an opaque storage key/reference;
- retrieve or authorize controlled access;
- delete only when an explicit domain-approved operation calls for it;
- translate provider-specific errors into application-level storage errors;
- never decide workspace membership or KYC permissions.

### KYC service responsibilities

- validate authenticated user and workspace membership;
- verify Tenant/KycDocument workspace ownership;
- enforce sensitive-document permissions;
- enforce document lifecycle rules;
- create/update KycDocument metadata transactionally;
- invoke the adapter only after domain authorization;
- issue controlled delivery only after authorization.

## 5. Provider Strategy: Cloudinary

Cloudinary remains the first implementation provider because it is already configured by the application, but P1.6 must not couple KYC domain models to Cloudinary-specific fields or URLs.

New KYC objects should use a dedicated private namespace/prefix and private delivery semantics. The implementation must use the provider's authenticated/private delivery mechanism rather than a normal public asset URL.

Recommended conceptual key format:

```text
kyc/private/workspace/<workspace_id>/tenant/<tenant_id>/<opaque_document_id>
```

The actual stored key should use a non-guessable identifier and must not include document numbers or filenames supplied by users.

Provider credentials remain server-side environment configuration only. They must never be returned through API serializers or included in logs.

## 6. File Validation Contract

Validation occurs before persistence of the KycDocument as an accepted uploaded object.

### Required checks

- authenticated upload endpoint only;
- allowlisted document categories;
- allowlisted MIME types;
- extension checked against the detected content type;
- maximum file size enforced server-side;
- empty files rejected;
- malformed/unsupported files rejected;
- filename treated as untrusted metadata;
- storage key generated server-side.

The initial P1.6 allowlist should be deliberately narrow (for example PDF and approved image formats) and configurable rather than accepting arbitrary files.

If a malware/content-scanning service is introduced later, the adapter boundary must permit a quarantine flow. P1.6 must not claim a document is safe merely because an extension or client MIME type passed validation.

## 7. Upload Flow

```text
Authenticated request
        ↓
Resolve workspace + Tenant
        ↓
Check active membership + upload permission
        ↓
Validate file size/type/content
        ↓
Generate opaque storage key
        ↓
Upload to private storage
        ↓
Create KycDocument metadata transactionally
        ↓
Create audit/verification event where contract requires it
        ↓
Return metadata only (never public file URL)
```

If metadata persistence fails after a provider upload, implementation must have an explicit cleanup/compensation path so orphaned private objects do not accumulate silently.

The preferred implementation pattern is: validate first, create an upload/quarantine reference, persist domain state, and clean up provider objects on transactional failure. Exact ordering may vary with provider constraints, but partial failure must be tested.

## 8. Controlled Download Flow

```text
GET /api/kyc/documents/<document_id>/download/
        ↓
Authenticate
        ↓
Resolve current workspace
        ↓
Load document with workspace boundary
        ↓
Check tenant/workspace ownership
        ↓
Check sensitive-document permission
        ↓
Check document state/access policy
        ↓
Create short-lived delivery grant
        ↓
Return controlled response
```

The endpoint must never accept an arbitrary provider URL or arbitrary storage key supplied by the client.

The preferred API behavior is a backend-controlled response. If the provider supports secure short-lived delivery, the backend may issue a narrowly scoped temporary grant after authorization. The grant must expire quickly and must not become a reusable permanent document URL.

## 9. Authorization Matrix

| Operation | Staff | Manager | Admin/Owner |
|---|---:|---:|---:|
| View normal KYC metadata | Yes | Yes | Yes |
| View/download sensitive documents | No | Yes | Yes |
| Upload/re-upload document | No | Yes | Yes |
| Submit KYC | No | Yes | Yes |
| Verify/reject KYC | No | Yes | Yes |
| Change KYC policy | No | No | Yes |

All operations additionally require:

- authenticated user;
- active workspace membership;
- document/tenant belongs to the current workspace;
- no cross-workspace object resolution;
- service-level permission checks, not serializer-only checks.

## 10. Workspace / RLS Boundary

Every new KYC storage metadata table is workspace-scoped and protected by the existing PostgreSQL RLS pattern.

Storage keys alone are never considered sufficient tenant isolation. A guessed or leaked storage key must not bypass API authorization.

The database boundary is:

```text
current workspace
      ↓
KycDocument.workspace
      ↓
KycDocument.tenant.workspace
```

The implementation must preserve both `USING` and `WITH CHECK` semantics for new workspace-scoped tables.

## 11. Serializer/API Contract

KYC serializers must expose safe metadata only.

Never expose:

- provider secret/configuration;
- permanent public asset URL;
- raw signed URL with long lifetime;
- internal storage credentials;
- arbitrary storage path accepted from the client.

A download operation is a separate authenticated endpoint rather than a passive `url` field on every KycDocument representation.

## 12. Legacy Tenant.id_document Strategy

The existing `Tenant.id_document` remains for backward compatibility during P1.6.

Rules:

- do not fabricate a KycDocument from an existing file without deterministic migration semantics;
- do not mark a new KycProfile VERIFIED merely because legacy KYC fields are populated;
- do not expose the legacy file through the new KYC download endpoint without an explicit compatibility/security decision;
- future writes should use the new KYC document service;
- a later migration may explicitly import legacy documents into private storage with audit metadata.

The global `DEFAULT_FILE_STORAGE` setting must not be treated as proof that a legacy Tenant file is private.

## 13. Deletion / Retention

P1.6 does not introduce automatic destructive deletion of KYC evidence.

Document deletion must be a domain-level operation with explicit authorization and retention policy. Rejection, replacement, or expiry does not automatically mean physical deletion.

When physical deletion is eventually allowed, the service must:

1. authorize the operation;
2. record the domain/audit action;
3. delete or quarantine the provider object;
4. handle provider failure explicitly;
5. never rewrite immutable verification history.

## 14. Threat Model / Adversarial Cases

The implementation must test at minimum:

1. unauthenticated download;
2. authenticated user from another workspace downloading by document ID;
3. inactive workspace member downloading;
4. Staff attempting sensitive document download;
5. Staff attempting upload/re-upload;
6. Manager accessing a document belonging to another tenant in the same workspace;
7. guessed/sequential document IDs;
8. client-supplied arbitrary storage key/provider URL;
9. public URL accidentally serialized;
10. oversized upload;
11. unsupported MIME/extension;
12. malformed file;
13. provider upload succeeds but DB transaction fails;
14. DB record exists but provider object is missing;
15. repeated download-grant requests;
16. expired delivery grant;
17. cross-workspace direct ORM access under RLS;
18. attempted bulk mutation of protected KYC metadata;
19. replacement creating an audit-preserving new document;
20. secrets/storage credentials appearing in logs or API responses.

## 15. Observability Contract

Safe audit information may include:

- actor user ID;
- workspace ID;
- tenant ID;
- document ID;
- action type;
- success/failure;
- timestamp;
- provider-neutral error category.

Never log:

- document contents;
- government ID/document numbers;
- raw provider URLs;
- signed delivery tokens;
- access credentials;
- uploaded file names where they contain avoidable PII.

## 16. Failure / Consistency Rules

Storage and database are separate systems, so P1.6 must explicitly test non-atomic cross-system failure.

Required behavior:

- no KycDocument row may claim a successfully stored object unless the storage reference is valid;
- provider upload failure must not create a VERIFIED document;
- DB transaction failure after upload must trigger cleanup/compensation;
- missing provider object must produce a controlled application error, never a silent public fallback;
- storage outage must not mutate KYC lifecycle status;
- KYC verification must remain a database/service operation independent of provider availability after metadata has been persisted.

## 17. Implementation Order

The locked implementation sequence is:

1. KYC models and workspace/RLS migration;
2. private storage adapter interface + Cloudinary implementation;
3. KYC domain services and lifecycle transitions;
4. authenticated API endpoints;
5. controlled download endpoint;
6. adversarial/security tests;
7. CI GREEN;
8. only then consider legacy-document migration/import.

No production model migration should be merged while the private-storage boundary is still undefined.

## 18. Non-Goals

P1.6 does **not** include:

- eSign provider integration;
- applicant portal;
- OCR-based automatic verification;
- Aadhaar/identity-provider API integration;
- automatic KYC decisioning;
- public document sharing;
- financial lifecycle changes;
- Lease lifecycle changes;
- automatic destructive document retention cleanup.

## 19. Final Security Decision

**APPROVED FOR IMPLEMENTATION after the P1.6 model/RLS design.**

The critical rule is locked:

> **KYC documents are private objects behind an application-controlled, authenticated, workspace-aware delivery boundary. A provider URL is never the authorization boundary and never the KYC source of truth.**

This design is the prerequisite for implementing P1.6 storage integration and KYC APIs without weakening existing workspace isolation, RBAC, RLS, or financial contracts.
