# P1.2 — Lease Hardening & Contract Verification

## Status

**P1.2 HARDENING IMPLEMENTED — CONTRACT VERIFICATION CANDIDATE**

This document records the verified Lease model contract before P1.2 is locked.

## 1. Model Contract

- `Lease.workspace` is a protected foreign key to `workspaces.Workspace` with reverse name `workspace.leases`.
- `Lease.occupancy` is a protected **OneToOneField** to `tenant.Occupancy` with reverse name `occupancy.lease`.
- Tenant identity is sourced through the existing Occupancy → Tenant relationship; Lease does not duplicate tenant ownership.
- `created_by` and `updated_by` are protected user relations with reverse names `leases_created` and `leases_updated`.
- Contractual financial values (`rent_amount`, `security_deposit`) are snapshots for the lease contract and do not replace or mutate the canonical Financial Core.

## 2. Lifecycle Contract

Allowed statuses are:

`draft`, `pending_signature`, `active`, `expired`, `terminated`, `cancelled`.

The allowed status set is enforced both by Django validation and a database check constraint.

Date integrity requires `end_date >= start_date`.

This model establishes lifecycle states but does not silently implement transition workflows, notifications, eSign, KYC, renewal mutation, or Occupancy state changes.

## 3. Renewal / History Boundary

The current P1.2 contract intentionally keeps Lease ↔ Occupancy as OneToOne.

Renewal/history must therefore be implemented by a future explicit version/renewal record or another reviewed history mechanism. A renewal must not silently overwrite the existing Lease as if it were a new historical contract.

Changing the OneToOne relationship is an architecture decision and is outside this hardening patch.

## 4. Database Contract

Migration dependencies are pinned to:

- `tenant.0011_delete_integrity`
- `workspaces.0006_rls_fail_closed`
- the configured swappable user dependency.

Explicit indexes:

- `lease_ws_status_idx`
- `lease_ws_start_idx`
- `lease_ws_end_idx`

All index names are within PostgreSQL's identifier-length limit.

Database constraints enforce:

- end date is not before start date;
- rent is non-negative;
- security deposit is non-negative;
- lifecycle status belongs to the contractual status set.

## 5. Workspace / Security Contract

- Lease workspace must match the Occupancy tenant workspace.
- Lease creator must be an active member of the Lease workspace.
- Workspace isolation is enforced at PostgreSQL level with RLS and FORCE RLS.
- Policy name: `workspace_isolation_leasinglease`.
- Cross-workspace Occupancy assignment is rejected.

## 6. Financial Boundary

Lease creation is contractual data creation only.

P1.2 does not create a competing receivable, payment, allocation, advance-credit, adjustment, late-fee, settlement, or ledger authority. Financial mutations remain under the locked P0 canonical services and ledger architecture.

## 7. Regression Contract

Dedicated regression coverage verifies:

- Occupancy tenant source and reverse relation;
- OneToOne Occupancy semantics;
- contractual related names;
- invalid dates;
- cross-workspace Occupancy rejection;
- inactive creator rejection;
- invalid lifecycle status rejection;
- negative financial-value database constraints;
- explicit short index names;
- PostgreSQL RLS/FORCE RLS and policy presence where PostgreSQL is available.

Constraint-violation assertions use transaction savepoints so one expected database error cannot poison the surrounding Django `TestCase` transaction.

## 8. Existing Contract Preservation

P0.1–P0.12 financial contracts remain authoritative. P1.2 extends the domain with a leasing contract layer and does not replace existing Occupancy or Financial Core semantics.

## Lock Gate

P1.2 may be marked **HARDENED / CONTRACT LOCKED** only after the latest branch HEAD passes the full CI workflow on the exact commit containing this hardening contract and its regression coverage.
